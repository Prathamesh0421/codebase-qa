Project reference

Multi-agent RAG over source code

Everything behind CodeQA — what it does, every decision and the alternatives rejected, the problems hit while building it, and the answers to the questions those decisions invite.

Explaining it

Three lengths. Interviews ask for all three, usually in this order.

30 seconds

It answers questions about unfamiliar codebases — "how does auth work here", "what happens between the route handler and the database". Generic RAG chunks source at arbitrary character boundaries and splits functions mid-body. This parses with tree-sitter and chunks at function and class boundaries, so every retrieved unit is syntactically complete. The part I care about: it also extracts the call graph, so when it retrieves a function it pulls in that function's callers and callees. That's what lets it explain a flow instead of a fragment.

Two minutes

Four layers. Indexing parses a repo with tree-sitter, chunks by function/class, extracts caller→callee edges, embeds, and writes to Postgres with pgvector. Retrieval is hybrid — dense vector search fused with Postgres full-text and an exact symbol index via Reciprocal Rank Fusion — then expands along the call graph. Reasoning is a LangGraph state machine: locate → trace → synthesize, where trace walks a cyclic call graph with bounded depth. API is FastAPI with SSE streaming, API-key auth, Redis rate limiting, and OpenTelemetry spans per stage.

The piece I'd point at is the eval harness. The whole premise is that call-graph expansion improves retrieval, so there's a labeled question set and a runner that measures precision@k for naive vs hybrid vs +graph. I built the naive baseline first specifically so there was something to measure against, and I never deleted it.

Five minutes — add the decisions

Then walk the decisions in section 05, and land on one war story from section 07. The HNSW partitioning one is the strongest: it's a real bug, it was found by measurement rather than reasoning, the obvious fix didn't work, and the eventual fix made a whole class of bugs impossible instead of less likely.

Problem & thesis

What's actually hard here, stated so the design reads as a consequence of it.

Engineers joining an unfamiliar codebase spend disproportionate time on structural questions. Answering them requires more than finding a relevant function — it requires knowing how that function connects to the rest of the system: who calls it, what it calls, where it sits in an end-to-end flow.

General-purpose "chat with your documents" RAG handles this badly for code, in two specific ways:

  • Chunking destroys syntax. Fixed character windows split functions mid-body. A chunk containing the back half of one function and the front half of the next is not a meaningful retrieval unit, and an embedding of it means very little.
  • Retrieval is call-graph blind. Even a perfectly retrieved function is an isolated snippet. The model can describe what it does, but not how it participates in a flow — which is precisely the information a new engineer needs.
The thesis

Retrieving a function plus its direct callers and callees produces measurably better retrieval than semantic similarity alone. Everything distinctive about this project follows from that claim — which is why the eval harness that tests it was moved ahead of the agent layer.

Flask is the anchor repo for evaluation because it has genuine multi-hop request flows: route → add_url_rule → full_dispatch_request → dispatch_request → view. "What happens between a request arriving and my view function running" is exactly the question naive RAG fails and call-graph expansion should win. Flatter libraries like requests were rejected as anchors for having too few multi-hop chains to demonstrate anything.

Architecture

Four layers, one database.

Indexing

Enumerate source files → parse with tree-sitter → emit function/class chunks with metadata → extract call edges → embed → upsert into Postgres. Runs as a background job, not in a request: indexing takes minutes.

Storage

One Postgres instance holds vectors (pgvector), chunk metadata, the symbol index, and the call graph. Redis holds the query cache and rate-limit buckets. Using one database rather than a dedicated vector store means hybrid retrieval is a join instead of a client-side merge across two systems with independent failure modes.

Retrieval

Three strategies behind one interface, selected by config: naive (dense only), hybrid (dense + full-text + symbol, fused by RRF), and hybrid+graph (hybrid, then call-graph expansion). All three stay runnable permanently so the comparison is reproducible at any commit.

Reasoning

A LangGraph state graph. Locate interprets the question and issues retrieval queries. Trace walks the call graph around the located chunks with bounded depth and cycle detection. Synthesize streams a grounded answer with file:line citations. A conditional edge routes back from trace to locate when context is insufficient, bounded by an attempt counter.

Request path

POST /v1/query
  → auth + per-key rate limit (Redis token bucket)
  → cache check (normalized question + repo scope)
  → locate    : hybrid retrieval, repo-scoped
  → trace     : recursive CTE over call_edges, bounded depth
  → synthesize: SSE token stream, citations verified before emit
  → OTel spans exported per stage; result cached

Design decisions

Each one names what was given up. A decision without a stated cost reads as an untested opinion.

Multi-repo, not multi-tenant

Context
The design doc scoped "one codebase at a time" and explicitly cut multi-tenancy. The requirement became "work on any repo".
Decision
Separate the two ideas. Multi-repo indexing is in — a repo registry, repo_id on every chunk, symbol and edge. Multi-tenancy stays cut — no per-org isolation, no auth boundaries between users.
Gave up
Any story about tenant isolation or per-customer data boundaries. That's a different project.
If asked
"Those are different requirements that sound similar. Indexing many repos is a data-modeling problem — scope every row by repo. Multi-tenancy is a security-boundary problem. I built the first and deliberately didn't claim the second."

Tree-sitter tag queries instead of per-language parsers

Context
Supporting "all languages" appears to mean writing an AST walker per language — the thing that makes multi-language support look impossible for one person.
Options
Hand-write extraction per language; or restrict to Python; or find a uniform mechanism.
Decision
Tree-sitter grammars ship queries/tags.scm declaring captures like @definition.function, @definition.class and @reference.call — the same mechanism GitHub uses for cross-language code navigation. One query-driven code path replaces N parsers. Adding a language ships a .scm file, not code.
Verified
Checked across nine grammars before designing around it. Definitions + calls: python, javascript, go, java, rust, ruby, php. Definitions only: typescript, cpp. No queries at all: c_sharp. Built in Phase 2 as 10 individually pinned grammar packages plus two override queries — 11 languages registered, 28 unit tests pinning the exact captures each query produces against real code.
Gave up
Precision. A hand-written walker with type information would resolve calls better. Tag queries are syntactic — they see foo(), not what foo resolves to.
If asked
"Languages carry a declared capability tier rather than silently degrading. Tier 1 gets real call edges; tier 2 gets chunks and approximate edges; tier 3 gets chunks and symbols only. The system reports which tier it used, so nobody mistakes an approximation for analysis."

Rejected a bulk grammar-pack dependency

Context
tree-sitter-language-pack on PyPI offers 371 languages behind one dependency — the obvious shortcut once the tag-query approach was decided, and worth checking before pinning ten packages by hand.
Red flags, checked before adopting
Its API is far larger than "grammar pack" implies — CodeChunk, SymbolInfo, DownloadManager, download_all — and that last pair matters: it fetches compiled native binaries at runtime rather than shipping them in the wheel. Publisher is xberg-io, a commercial org on GitHub created October 2025, not the canonical tree-sitter maintainers. The repo itself is real and active (454 stars, pushed same-day) — this isn't a typosquat — but young and feature-bloated for what should be a thin grammar wrapper.
Decision
Rejected. This project clones and parses arbitrary third-party repositories. A dependency that downloads and dynamically loads native code from the network at runtime reintroduces exactly the supply-chain risk that "tree-sitter parses but never executes" exists to rule out — the exposure moves from the untrusted repo being parsed to the parser itself.
Gave up
Convenience. Ten explicit dependencies and two hand-written override queries instead of one. Each was installed and its tags.scm content inspected directly rather than trusted from memory.
If asked
"I don't reject a dependency for being young — I reject it for what it does at runtime combined with what this system does with untrusted input. A grammar pack that only unpacks wheels at install time would have been a fine shortcut; one that fetches binaries while indexing a stranger's repository is a different risk profile entirely."

Recursive CTEs enumerate paths, not a BFS tree — and the differential test caught it

Context
The mental model going in was "WITH RECURSIVE ... CYCLE is a BFS with built-in cycle safety." That's half right. CYCLE stops a single path from repeating a node it already visited; it says nothing about two independent paths converging on the same node — a diamond shape (a→b→d and a→c→d) isn't a cycle at all, so nothing prevents d from appearing twice.
How it was found
Not by reading documentation closely enough — by writing the differential test and having it fail. traverse_sql returned d at depth 2 twice; traverse_networkx, built on networkx's own shortest-path BFS, returned it once. The disagreement was the signal, not a bug report.
Decision
SELECT DISTINCT ON (chunk_id) ... ORDER BY chunk_id, depth keeps each node's minimum-depth occurrence. That forces the query's ORDER BY to start with chunk_id rather than depth — so truncation to graph_max_nodes moved out of SQL entirely; the query returns everything reachable, and Python sorts by (depth, chunk_id) and slices, which keeps the closest nodes when truncating rather than an arbitrary chunk-id-ordered subset.
Verified, not assumed, either direction
EXPLAIN ANALYZE confirmed DISTINCT ON defeats Postgres's early-termination on a wide fan-out (5.4ms vs 0.03ms on a synthetic 5000-edge case — it must fully materialize before it can sort). Accepted rather than engineered around: correctness matters more here, and graph_max_depth (default 2) remains the real bound on database work regardless of width.
Gave up
The specific optimization verified in the first pass at this query (unordered LIMIT stopping the recursion early). Kept as documented, superseded reasoning in the code rather than deleted — the comment explaining why the first approach doesn't survive contact with correct deduplication is worth more than a clean diff that hides the tradeoff.
If asked
"A recursive CTE with a CYCLE clause gives you cycle-safety, not deduplication — those are different guarantees that look similar until a diamond-shaped dependency proves otherwise. I found this because I built an independent second implementation specifically to disagree with the first one if it was wrong, not because I read the semantics carefully enough the first time."

Call resolution: an ordered heuristic that refuses to guess

Context
A call site names a bare identifier — self.dispatch_request() captures the callee name dispatch_request, with no receiver type information. Real Flask defines that name on three different classes. Without type inference (a stated non-goal), resolving it correctly requires a different kind of evidence entirely.
Decision
An ordered sequence of heuristics, each requiring an unambiguous match before it's trusted: zero candidates → unresolved; exactly one candidate anywhere in the repo → exact; multiple candidates but exactly one defined on the caller's own class → approximate; multiple candidates but exactly one in the caller's own file → approximate; anything left → unresolved. No tier ever picks among several remaining candidates — that would be a guess wearing a resolved edge's clothes.
Verified against
The literal case that motivated it: Flask.full_dispatch_request calling dispatch_request, ambiguous across Flask, View, and MethodView. The same-class tier correctly picks Flask.dispatch_request — confirmed through the full indexing pipeline against the real fixture, not just the isolated resolver logic.
Gave up
Recall on genuinely ambiguous calls. A cleverer heuristic (e.g. "prefer whichever candidate is textually closest") could resolve more edges, but every extra tier is another way to be confidently wrong. 787 of 1110 edges in the real Flask index are unresolved — mostly calls into external libraries with no chunk in the index at all, which is the honest, expected shape.
If asked
"Why not resolve more calls by guessing when there's a plausible-looking candidate? Because an edge in this table is meant to be trustworthy enough to walk during retrieval. A wrong edge that looks identical to a right one is worse than a missing edge, which at least fails visibly."

The retrieval strategy interface, built before it had a second implementation

Context
Phase 5 needs exactly one retrieval strategy: naive cosine similarity. Hybrid and hybrid+graph don't arrive until Phase 8.
Decision
Design the full RetrievalStrategy protocol now — retrieve(conn, repo_id, query_text, embedder, top_k) — with naive as the only implementation, and hybrid/hybrid_graph raising a clear NotImplementedError naming the phase that adds them.
Reason
This is normally the shape of premature abstraction the project's own principles warn against — an interface for implementations that don't exist yet. It earns an exception here because the entire evaluation story is a comparison across three strategies at the same commit, selected by one config value. Building naive as a bare function first and refactoring it behind an interface once hybrid exists risks the naive path quietly changing shape during that refactor — which breaks the reproducibility the comparison depends on.
Gave up
Nothing built for hybrid or hybrid+graph beyond their signatures — no speculative lexical-search or graph-traversal code exists yet. The interface is committed to; the future implementations are not.
If asked
"Doesn't this contradict 'don't design for hypothetical future requirements'? Normally yes. The exception is that the requirement isn't hypothetical — Phase 8 and Phase 9 are both already scoped, and the interface is the thing being measured, not a guess at one."

Postgres recursive CTE for traversal, networkx as test oracle

Context
The design doc specified networkx for the call graph.
Problem
networkx is in-memory. The edges already live in Postgres, so every query would either load a repo's whole graph or maintain a second persistence format — worse with many repos.
Decision
Traversal behind an interface with two implementations. Production is WITH RECURSIVE … CYCLE (Postgres 14+), which gives bounded depth and built-in cycle detection, repo-scoped, in one query with no memory load. networkx becomes the reference implementation used only in tests.
Bonus
Differential testing: assert both implementations produce identical traversals on fixtures. Two independent implementations agreeing is far stronger evidence than one implementation passing hand-written expectations.
Gave up
Graph algorithms beyond traversal. Centrality or community detection would be painful in SQL — but the system doesn't need them.
If asked
"Why not a graph database? It would mean a second system to run, sync and fail independently, to serve bounded-depth traversal that Postgres does natively. The edges have to live somewhere transactional next to the chunks anyway."

Evals moved ahead of the agent layer

Context
The original plan put the eval harness at days 13–15, after agents and production features.
Decision
Move it to immediately after retrieval lands. "Call-graph expansion improves retrieval" is a retrieval claim — testable with no agents involved.
Reason
If the hypothesis is weak, that is the single most important finding the project can produce. The original schedule discovers it with three days left. It also means every later phase is guarded by a regression harness, which is what "CI for answer quality" actually requires.
Gave up
An impressive demo earlier. The agent pipeline is the flashy part and it now comes later.
If asked
"I sequenced it so the riskiest assumption gets tested first. The agents are engineering I'm confident I can finish; whether the retrieval idea works is the actual unknown."

A second recall metric, because the obvious one can't see graph expansion

Context
HybridGraphStrategy.retrieve() returns primary + expanded, where primary is exactly HybridStrategy's own fused top-k, unchanged.
Problem
Precision@k / recall@k computed the conventional way is therefore numerically identical between hybrid and hybrid_graph — always, by construction, regardless of how much graph expansion actually contributes. Graph-expanded chunks live entirely past the k cutoff; a fixed-k metric is structurally blind to them.
Decision
Report both: the fixed-k row (printed with a note that the identity is expected, not hidden), and a second metric — recall computed over hybrid_graph's full returned list, primary plus expansion. Only the second one can answer "did graph expansion help."
If asked
"Why not just report the full-list metric and drop the identical row? Because the identity itself is informative — an interviewer asking why hybrid_graph's headline metric equals hybrid's gets a much better answer from a printed row and one sentence than from a metric that quietly disappeared."

Eval gold sets written from source, not from the call graph

Context
Multi-hop questions need gold sets spanning several connected functions — the natural temptation is to pick them by walking call_edges from a plausible starting point.
Problem
Doing that makes the eval circular: measuring whether call-graph expansion finds chunks that were selected via the call graph only proves traversal works, which Phase 7's differential test already proved. It would look like new evidence for the retrieval thesis while being none.
Decision
Every question's gold set was written by reading Flask's actual source and deciding, independently, what a complete and correct answer would have to cite. call_edges was consulted only afterward — to observe whether the gold sets turned out graph-adjacent, not to construct them.
If asked
"How do I know the gold sets aren't just accidentally graph-adjacent anyway, since real code chains through calls? I don't rule that out — real multi-hop flows are often call-graph-adjacent, which is exactly why the technique works. What matters is that adjacency was discovered, not assumed as a selection filter."

A real conditional edge in the agent graph

Context
The design doc justified LangGraph with "native support for cycles" — but locate → trace → synthesize is a straight line. The cycles were in the call graph, not the agent graph.
Problem
That's a defensibility hole. The obvious follow-up — "so why not three function calls?" — had no good answer.
Decision
Give the agent graph a genuine cycle: if trace finds insufficient context, route back to locate to re-query with refined terms, bounded by an attempt counter in state.
Gave up
Latency in the retry path, and a new non-termination risk that the attempt counter has to bound.
Built (Phase 10)
Proven to actually fire, not just exist, by a test that mocks two different trace verdicts in sequence (INSUFFICIENT, then SUFFICIENT) and asserts locate ran twice — a test asserting only that the edge is wired into the graph couldn't tell "the cycle exists" from "the cycle executes correctly."
If asked
"Honestly, for a purely linear pipeline LangGraph would be overkill — three function calls would do. It earns its place because of the retry edge, which needs conditional routing and shared state. I'd rather state that than pretend the linear version justified the dependency."

The retry edge is measurably redundant with call-graph expansion

Context
Ran the retry mechanism against real Flask under all three retrieval strategies, scoring recall on Phase 9's request-lifecycle gold set before and after the retry fired, rather than assuming the mechanism "works" because it executes.
What the numbers show
Under naive: recall 0.25 → 0.38 after retry. Under hybrid: 0.12 → 0.38, precision also improving (0.10 → 0.20). Under hybrid_graph: 1.00 → 1.00 — attempt 1 already sits at the recall ceiling via call-graph expansion alone, so the retry can only add noise, and precision measurably drops (0.32 → 0.29).
Reading
The agent's re-query loop and Phase 8's call-graph expansion are two different mechanisms solving the same underlying problem: a single query embedding can't reach every relevant chunk in a multi-hop flow. Whichever one already ran captures most of the available gain, which makes the second one redundant on the same question, not additive.
Decision
Kept the retry edge regardless of the redundancy with hybrid_graph specifically — a repo where bounded call-graph expansion (graph_max_depth=2, tier2/3 languages with degraded call graphs, or a chunk simply outside expansion's reach) doesn't recover enough context is exactly the case the retry would still earn its keep on.
If asked
"Doesn't this mean the retry is pointless with your recommended default strategy? On this one question, yes — that's the honest reading of the number, and I'd rather say that than claim a universal win the data doesn't support. It stops being redundant the moment retrieval alone can't reach the answer, which is a real, not hypothetical, failure mode for graph expansion bounded by depth."

Sorting chunks at display time instead of trusting accumulation order

Context
--agent's Retrieved: list is built from chunks accumulated across possibly-multiple locate attempts (merge_chunks), then printed the same way the direct, single-retrieval CLI path already did.
Problem
Found in the first real run against Flask, reading the actual output rather than trusting the tests: a second locate attempt's real-scored primary chunks printed after the first attempt's 0.000-sentinel graph-expanded ones. merge_chunks only promises accumulation order (existing first, then new), which happened to equal display order in the single-attempt case the direct CLI path always has, but stopped being true the moment a second attempt's own primary-then-graph ordering got appended after the first's.
Decision
sort_for_display: real scores descending first; any chunk graph expansion touched (identifiable by "graph" in source, since the sentinel score is never comparable to a real one) grouped at the end, regardless of which locate attempt found it.
If asked
"How did you catch this? Not from the test suite — every existing test asserted on chunk identity and score values, never on printed order. It surfaced from reading one real CLI run's output end to end instead of stopping at green tests, the same discipline that caught the Phase 8 hybrid-retrieval regressions."

Reciprocal Rank Fusion for hybrid retrieval

Context
The doc said results are "merged and reranked" without specifying a method.
Problem
Cosine similarity and full-text ts_rank are on incomparable scales. Summing or weighting them requires tuning constants with no principled basis.
Decision
RRF: score each document by Σ 1/(k + rank) across result lists. It consumes ranks, not scores, so scale mismatch stops mattering. Roughly ten lines, no model, no added latency.
Gave up
Some ceiling. A cross-encoder reranker would likely do better — so it becomes a measured upgrade in the eval harness rather than an unexamined default.
If asked
"Dense retrieval is semantically strong and lexically weak. Identifiers need exact matching — ask where dispatch_request is defined and an embedding returns things that feel like request dispatching. That's the argument for hybrid on code specifically."

Symbol matching filters by token shape, not a stopword list

Context
The symbol component of hybrid retrieval matches bare tokens extracted from the raw query text against real symbol_names, exact match, no fuzziness.
Problem
Found running against real Flask, not the hand-built fixture: ordinary English words in a question are frequently also real symbol names in real code. "Flask", "view", and "request" are a class and two methods in Flask's own source — unfiltered, the entire 1500-line Flask class chunk won an exact match and outranked the actual answer in RRF fusion.
Decision
filter_symbol_candidates keeps a bare token only if it contains an underscore or an internal (non-first-character) capital letter — dispatch_request and SessionManager qualify, "flask" and "view" don't. Shape, not a hand-maintained word list.
Gave up
Exact-match boost for a real symbol that happens to be a single, all-lowercase word (a function actually named dispatch, say). Accepted: there's no shape-based way to distinguish that from the English verb, and false positives from ordinary words are the more damaging failure of the two.
If asked
"Why not a stopword list? Because it can't tell 'Flask' the framework's class name from 'flask' the container — dictionary membership doesn't encode that distinction, but how the identifier is written does. A stopword list would also need constant upkeep as new false positives turned up; shape-gating doesn't."

Graph-expanded chunks keep their pool membership in the label, not just "graph"

Context
HybridGraphStrategy expands beyond hybrid's fused top-k by walking the call graph from every primary result, and labels what it adds source="graph" so Phase 9's eval can tell what call-graph expansion is actually contributing.
Problem
The first version excluded any chunk already present in any component's candidate pool from graph expansion entirely — reasoning that if vector/lexical/symbol search already knew about it, graph didn't "find" it. Verified against real Flask that this was wrong in a worse way than the labeling imprecision it fixed: Flask.dispatch_request was ranked #10 by raw vector similarity (inside vector's own candidate pool) but pushed out of the fused top-k by chunks that matched multiple components — so excluding pool members silently dropped it from hybrid_graph's results altogether, both not-primary and not-graph.
Decision
Keep expansion inclusive of anything not already a primary result. Label precisely instead: source is "graph" alone only when no component's pool contained the chunk at all; "graph+vector" etc. when it did, just not highly enough to survive that component's own fusion into top-k.
If asked
"A chunk a component's pool touched but didn't rank into the final answer is still real information worth surfacing — what it doesn't deserve is being credited to the wrong mechanism. Phase 9 reads source == "graph" exactly as 'nothing else came close,' and getting that string precisely right is the whole point of carrying it at all."

Local and hosted embeddings behind one interface

Context
Provider undecided; deployment target is a hosted backend.
Tension
Local models mean torch — roughly 2GB in the image plus inference RAM, which a small hosted instance doesn't have. Hosted APIs mean rate limits, which make bulk indexing slow and eval runs non-reproducible.
Decision
Both, behind one interface. Local for dev, CI and evals; hosted for the deployed image. The interface was needed anyway to carry model name and dimension.
If asked
"Embedding provider is chosen by indexing throughput, not answer quality. A free tier with per-minute caps can't embed a few thousand chunks reproducibly, and irreproducible eval runs are worse than slightly worse embeddings."

No ORM

Decision
Raw psycopg and plain numbered SQL migrations.
Reason
The interesting queries — HNSW vector search, RRF fusion, recursive CTE traversal, partition management — are all things an ORM obscures rather than helps. Alembic is heavy when there's no ORM to autogenerate from.
Gave up
Autogenerated migrations and typed row mapping. Both are written by hand instead.

A job boundary the design doc lacked

Context
Indexing an arbitrary repo takes minutes; an HTTP request can't hold it.
Decision
POST /v1/repos returns a job id; a status endpoint reports progress; a worker polls the index_jobs table with heartbeats so a dead worker's job is reclaimed rather than stuck in running forever.
Gave up
Simplicity. Deliberately not Celery — a Postgres job table plus a polling loop is about fifty lines and adds no broker to operate.

One containment check does the whole grounding job

Context
The plan describes grounding as three steps: claimed citation → chunk actually in context → line range actually exists in that file.
Decision
Implemented as a single check, not three: a citation is grounded if some chunk genuinely in context has that exact file and its real start_line/end_line contain the claimed range. A chunk's own bounds are already ground truth — extracted by tree-sitter from real source in Phase 3 — so a claimed range contained inside one is automatically a real range in a real file. The three-step description and the one-check implementation aren't in tension; the chunk's own provenance is what collapses them.
Boundary allowed
A claimed range may narrow a chunk's real bounds (citing a few lines within a bigger function is a legitimate, more precise citation) but never extend past them in either direction — that's a partial fabrication, not a narrowing. Covered by its own test, distinct from the "wholly fabricated range" case.
If asked
"Why not check the file's real line count too, separately? Because it can't add information the chunk-containment check doesn't already have — a chunk's range can't exceed its file's real length, since it was parsed from that file. A separate file-length check would be redundant work reaching the same answer through a slower path."

Grounding flags after the stream, it doesn't suppress before render

Context
Phase 10's synthesize_node already streams tokens live through a LangGraph custom writer channel — an established, tested contract this phase inherited rather than reopened.
Tension
ground_answer needs the complete answer text — a citation can't be checked from a line number that's only half-arrived. By the time it can run, both codeqa ask paths have already streamed the tokens live, including any that turn out to be an ungrounded citation.
Decision
The function's own contract stays literal — result.text never contains the raw fake citation, a marker replaces it, which is exactly what a non-streaming caller would show. The CLI's job once streaming is done is different: print a clear warning listing what was dropped, since it can't retroactively edit what a terminal already displayed.
Gave up
A literal reading of "dropped, not rendered" for the interactive CLI specifically. Getting it would mean buffering the whole answer server-side before the first token is shown — a real latency cost the terminal UX wasn't worth paying for, on a path where the function's own output already keeps its word for any caller that doesn't stream.
If asked
"A live SSE endpoint (Phase 14) faces the identical choice — true pre-render suppression there means buffering server-side before the first byte goes out. Same trade, same honest cost, whichever surface does it."

SSRF guard: an allowlist, not DNS resolution and IP-range checks

Context
Server-side cloning of a user-supplied git URL is a classic SSRF surface — the URL could point at 169.254.169.254 or an internal service instead of a real public repo.
Options
Resolve the hostname and reject any resolved IP that's private, loopback, or link-local; or reject any host that isn't on a small allowlist of known public git-hosting domains.
Decision
The allowlist. config.py's allowed_clone_hosts field already existed from the Phase 0 scaffold, defaulting to github.com/gitlab.com/bitbucket.org — validate_clone_url just needed to enforce it. No DNS resolution happens at all; a URL whose host isn't on the list is rejected before any network call.
Gave up
Support for cloning from an arbitrary self-hosted git server out of the box. Accepted: the allowlist is a config field, not a hardcoded constant, so a self-hosted deployment adds its own host explicitly rather than the guard silently trusting anything that isn't obviously private.
If asked
"An IP-range check has to resolve DNS and then worry about the resolved address changing between the check and the actual clone — a TOCTOU-shaped problem. An allowlist sidesteps it entirely: the question isn't 'what IP does this resolve to right now,' it's 'is this a host we've decided to trust,' which doesn't need resolving at all."

The heartbeat thread gets its own database connection

Context
A running job's heartbeat needs to tick on an interval while index_repo runs synchronously and can take minutes — a background thread is the obvious shape.
Decision
The heartbeat thread opens its own psycopg.connect(), separate from the worker's main connection. A psycopg Connection is not safe to use concurrently from two threads, and the main thread is mid-way through a long sequence of index_repo queries at the exact moment the heartbeat thread would otherwise be issuing its own on the same connection.
If asked
"Sharing one connection across the heartbeat thread and the indexing work looks like it would work in a quick test, because SQLite-style single-writer semantics make people expect a connection object to just serialize concurrent use. psycopg doesn't guarantee that, and the failure mode — interleaved protocol state between two threads issuing queries at once — is exactly the kind of thing that wouldn't show up until it did, unpredictably, under real timing."

Incremental diffing compares content hashes against Postgres, not two git commits

Context
The obvious design for "what changed since last time" is git diff old_sha new_sha --name-status as a cheap candidate list, with files.blob_sha as a backstop against git's false positives (a file touched then reverted within the range).
Problem
Phase 12's clones are --depth 1. By the time a repo is re-indexed, the OLD commit a diff would need as one endpoint may no longer be reachable in that shallow checkout at all — the two-commit diff can simply fail to run.
Decision
Never diff between two commits. Compare each file's CURRENT blob_sha against what's already stored in Postgres from the last run — this needs no git history whatsoever, only the current checkout, which any depth-1 clone already provides. Unchanged / changed / added / removed all fall out of that one comparison, uniformly for git_url and local_path repos alike.
If asked
"The false-positive argument for blob_sha is the one that shows up first, but it's not the strongest one here. The strongest one is that it sidesteps needing two-commit git history at all, which a shallow clone might not even have by the time it matters."

The call graph is rebuilt fresh every run, not diffed incrementally

Context
resolve_and_persist (Phase 6) already deletes and re-inserts a repo's entire call_edges set on every call — an existing, untouched contract this phase builds on rather than reopens.
Decision
Re-extract call sites from every currently-present file — touched or not — on every incremental run, then let resolve_and_persist do its normal full rebuild. Only chunk-level embedding is genuinely incremental; graph rebuild cost still scales with repo size, not with how much changed.
Why this is actually the simpler, more correct answer
The alternative — patch just the touched files' own edges — has a real gap: an untouched file B that calls into a changed file A loses its edge the instant A's changed chunk is deleted (the FK cascade takes the edge with it), and nothing would ever re-create it without re-scanning B too. A full rebuild from a fresh extraction pass makes that gap impossible by construction, and it's affordable specifically because tree-sitter parsing is cheap relative to embedding (Phase 4's own measurement) — so re-parsing every file to get this guarantee for free is a good trade, not a compromise.
If asked
"What happens to a call edge pointing at a chunk that just got deleted? Nothing dangles, ever — there's no edge table state that persists across the delete, because the whole table gets rebuilt from scratch immediately after, from a complete and current view of every file's chunks. The question doesn't really apply to this design."

Phase 0 — Scaffold and configuration Done

Two details worth being able to defend. Phase 1 — Schema and migrations Done

Seven tables — repos, files, chunks, symbols, call_edges, index_jobs, api_keys — plus a forward-only migration runner.

What the schema encodes

  • repo_id on every retrievable row, denormalized deliberately. It could be reached by joining through files, but it belongs in the WHERE clause of every query directly, and the recursive CTE would otherwise re-join at every recursion level.
  • chunks partitioned by repo_id — a correctness fix, not an optimization. See the first war story.
  • Composite foreign keys into chunks (repo_id, id), so a cross-repo edge is a constraint violation rather than a silent quality bug.
  • last_indexed_sha from day one, because incremental re-indexing keys off it and backfilling state you no longer have is impossible.
  • files.blob_sha, so an incremental run skips files git reports as touched but whose content is unchanged — reverted edits, formatter rewrites.
  • A generated tsvector column beside the vector, maintained by Postgres so it cannot drift from content.
  • edge_resolution — exact / approximate / unresolved — plus the raw callee name, so approximations stay auditable and are never rendered as certain call paths.
  • One live index job per repo, via a partial unique index on status IN ('queued','running'). Two concurrent indexers would interleave upserts and leave a repo half-indexed behind a last_indexed_sha claiming otherwise.

What the migration runner does beyond running files

  • Drift detection. Each applied migration's sha256 is recorded; editing a file after it applied is a hard error. Prevents the failure where an edit works on a fresh machine and production never applies it.
  • Checksums the raw template, before substitution. Substituted values come from config and legitimately differ between environments; the file must not. Hashing rendered SQL would flag every environment difference as tampering.
  • Advisory lock. Concurrent boots serialize instead of racing on CREATE TABLE — the normal case when several containers start at once.
  • Transactional DDL. Postgres lets DDL participate in transactions, so a migration failing partway leaves no partial schema, and the schema_migrations insert is in the same transaction as the change it records.
  • Dimension verification. After migrating, read the deployed vector dimension via format_type and refuse to boot on a mismatch with config.

Verification: 9 integration tests green against Postgres 17.11 / pgvector 0.8.6 — idempotence, dry run, drift, database-ahead-of-checkout, dimension mismatch, atomicity, and three discovery-validation cases.

Why integration tests, not mocks

Idempotence, drift, atomicity and dimension enforcement are properties of the runner's interaction with database state. Mocking psycopg would assert that the mock behaves like the code — always true, proves nothing. The same reasoning produced the measured HNSW finding below.

Phase 2 — Language layer Done

A grammar registry and one query-execution path (extract_tags) that every tier1/tier2 language runs through. Nothing in that function is language-specific — language knowledge lives entirely in query text, verified against real parse trees before being written.

What got built, and what got rejected first

The obvious shortcut for "all languages" was a bulk grammar-pack dependency — 371 languages behind one pip install. Checked before adopting it and rejected: its API downloads compiled native binaries at runtime, published by a young commercial org, not the canonical tree-sitter maintainers. For a system that parses arbitrary third-party repositories, that is the wrong place to introduce a runtime network fetch of native code. See the decision above for the full comparison. Ten official grammar packages are pinned individually instead, each verified by installing it and inspecting its actual tags.scm content directly — not assumed from documentation.

Two gaps needed override queries, and both surprised in a different way

  • TypeScript's own tags.scm is missing more than call references — no function_declaration or class_declaration at all, only the abstract_* variants. Ordinary code produces nothing from the upstream query alone. The fix borrows JavaScript's patterns directly, verified by parsing real TypeScript — including confirming the same query survives JSX syntax in the separate TSX grammar, since .tsx uses a different grammar entry point than .ts.
  • C++ has definitions but zero call references, and both obj.method() and obj->method() turned out to resolve to the identical field_expression node shape in this grammar — one override pattern covers both syntaxes, confirmed by parsing both forms rather than assumed from C++ syntax rules.

A mechanical trap that would have silently produced wrong data

tree-sitter's Python API offers two ways to run a query: QueryCursor.captures() returns a flat dict per capture name, and QueryCursor.matches() groups captures by which pattern match they came from. Multi-function files exposed the difference — .captures() would in general lose the correspondence between a specific @name and its @definition.function when several functions exist in one file, since both land in the same flat list with no guaranteed alignment between them. extract_tags uses .matches(), and test_multiple_definitions_paired_with_correct_names pins the correct pairing so a future refactor toward the more obviously named .captures() method fails loudly instead of silently mislabeling functions.

Verification: 28 unit tests green — 11 languages detected correctly by extension, tier assignment for all three tiers, real extraction against Python/JavaScript/TypeScript/TSX/C++/C#, JSX parsed without error in both the plain JS and TSX grammars, the #not-eq? predicate confirmed to actually exclude constructor from method definitions (proving real tree-sitter predicates are honored, not just silently ignored), and confirmation that non-definition captures like @doc and @local.scope never leak into results.

Phase 3 — AST-aware chunking Done

Turns Phase 2's Tags into Chunks matching the chunks table: (kind, symbol_name, qualified_name, start_line, end_line, content, content_sha). One invariant governs the whole module: content is always the verbatim, syntactically complete span of a single definition — never truncated, never re-windowed at a fixed character count, regardless of size. A 500-statement function is one unsplit chunk; splitting it would undo the entire quality claim this project makes over naive RAG.

The reclassification problem, and why it's one rule, not two

Python's tags.scm has no definition.method at all — every function, top-level or nested, is definition.function. Checked PHP while building this and found the identical gap: method_declaration is also tagged definition.function. Rather than special-case both languages, the chunker reclassifies any function-kind tag whose byte range is contained by an enclosing class/interface/type tag into a method — one rule that happens to fix two languages, and is a no-op for grammars (JS, Go, Java, Rust, Ruby) that already distinguish methods structurally.

That containment check was then verified not to apply everywhere it plausibly could. Go's receiver methods and Rust's impl-block methods looked like they should qualify the same way — until parsing real code showed both are byte-range siblings of their struct/type, not children of it. A Go method's span starts only after its struct's span already ends. qualified_name stays None there, and it's pinned as expected behavior in the tests, not left to be "discovered" later as a bug.

Verification: 17 unit tests green, including containment reclassification for Python and PHP, confirmation that JS's own method-tagging agrees with containment rather than conflicting, the Go/Rust sibling gap pinned as intentional, interface/struct/mod mapping to the schema's four chunk kinds, the whole-file fallback for tier3 languages and definition-free files, and a 500-statement function proven to remain one unsplit chunk.

A detour: a segfault, mitigated here and root-caused in Phase 4

Running the full suite crashed the interpreter outright — a Fatal Python error: Segmentation fault inside a compiled tree-sitter binding. Confirmed the indexing code was not at fault, bisected to a specific test-file ordering, ruled out free-threading, GC timing and assertion rewriting one at a time, and shipped process-level test isolation as a verified mitigation. It came back in Phase 4 on a real repository, where it turned out to be a tree-sitter 0.26.0 regression — pinned below it, and this workaround deleted. Both halves are in War Stories; the pair is the strongest debugging evidence in this project.

Phase 4 — Embeddings and the indexing pipeline Done

Where Phases 1–4 finally connect: schema, language detection, chunking and embedding all have to agree for one index_repo() call to work. codeqa index on the Flask fixture produces 446 chunks from 24 files in 4.5s — 308 methods, 81 functions, 53 classes, 4 whole-file fallbacks, every vector 384-dim.

Batching is measured, not assumed

The plan claims "batching dominates indexing throughput," so it got measured rather than asserted: 3.5x on 200 chunks (1.58s one-at-a-time vs 0.45s at batch size 64). That number is the reason index_repo chunks every file first and embeds the whole repo in one batched call, rather than the more obvious embed-as-you-walk — most files don't have enough chunks to fill a batch on their own.

Two pgvector behaviours worth knowing before writing persistence code

  • Vectors are stored as float4, so a Python float64 list round-trips lossily (0.1 becomes 0.10000000149011612). Harmless, but it means comparing embeddings for equality is always wrong — change detection uses content_sha instead.
  • A vector used as a query parameter needs an explicit ::vector cast. Inserting into a known vector column adapts automatically, but in ORDER BY embedding <=> %s Postgres infers double precision[] and no vector operator resolves. Found by trying it, not by reading about it.

The guard that catches what Postgres can't

A dimension mismatch is caught by the database — the column is vector(N). The dangerous case is two different models at the same dimension: those vectors insert cleanly and compare as though they meant the same thing, corrupting similarity search invisibly. So check_embedder_matches_repo compares model name and dimension against the repos row before any file is even walked, and refuses to proceed.

A finding that justified a schema column

Real Flask defines dispatch_request three times — on Flask, View and MethodView. My first test asserted there was one, and was wrong. That's exactly why chunks carry qualified_name and not just symbol_name: retrieving "dispatch_request" is ambiguous, and a citation that can't say which class it came from is a citation that can't be verified.

Verification: 97 tests green. Beyond the Flask end-to-end run: embedding order preservation, batch size not affecting output, both dimension guards, re-indexing being idempotent rather than duplicating, editing a file replacing (not appending) its chunks, one bad file not aborting a whole run, gitignore directory-pattern matching (including that mydist/ is not matched by dist/), and _blob_sha matching real git hash-object output byte for byte.

Phase 6 — Call-graph extraction Done

The differentiator. Every call site becomes a reference.call tag (Phase 2), attributed to its enclosing function or method chunk by the same byte-span containment logic Phase 3 uses for class/method reclassification — extracted into a shared spans.py rather than duplicated a second time. Resolving the bare callee name to a real chunk elsewhere in the repo is a separate, repo-wide pass that only runs once every file's chunks exist, since a callee can be defined in a file processed earlier or later than its caller.

The plan's own "done when" bar didn't survive contact with the real source

The original target was a 3-hop chain: full_dispatch_request → dispatch_request → view. Reading the actual line before assuming it would work: dispatch_request invokes the view via self.ensure_sync(self.view_functions[rule.endpoint])(**view_args) — a call on the return value of another call, not a named symbol. Extracting tags from that exact line confirmed it: only ensure_sync is captured; nothing named "view" exists to capture. This is real dynamic dispatch, structurally invisible to any syntactic query — not a bug, and not something a cleverer query pattern fixes. The bar was corrected rather than forced: the achievable 2-hop chain (full_dispatch_request → dispatch_request) is what's verified, and the third hop's absence is asserted explicitly in a test rather than silently missing.

That 2-hop chain turned out to be the best possible test case

Real Flask defines dispatch_request three times — on Flask, View, and MethodView. Resolving full_dispatch_request's call to it correctly requires the same-class heuristic to actually work, not luck: with only one candidate the edge would trivially resolve exact and prove nothing about disambiguation. Confirmed: resolution='approximate', correctly pointing at Flask.dispatch_request and not the other two.

Verification: 25 new tests, 150 total green. The pure resolver logic is tested with the exact three-candidate shape Flask produces, independent of the database; the full pipeline is tested against both a synthetic repo reproducing that same shape and the real Flask fixture. Indexing all of Flask produces 1110 call edges — 264 exact, 59 approximate, 787 unresolved. The high unresolved count is the honest picture, not a shortfall: most calls in a real application reach into external libraries with no chunk in the repo's own index at all.

Phase 7 — Graph traversal Done

Two implementations of "what's reachable from this chunk, safely" — traverse_sql, one WITH RECURSIVE ... CYCLE query, and traverse_networkx, calling networkx's own single_source_shortest_path_length rather than a hand-rolled loop dressed up as an independent implementation. networkx stays a lazy import inside the two functions that need it — it's a dev-only dependency, and this module also holds traverse_sql, which Phase 10's trace agent imports into the deployed image.

The differential test earned its keep immediately

Two real bugs surfaced before either implementation was trusted, both caught by disagreement between the two, not by inspection. First: CYCLE only detects a node repeating within one path — a diamond shape (a→b→d and a→c→d) isn't a cycle, so nothing stopped d from being returned twice. Second, and easy to miss by symmetry: the callees-direction recursive term selects callee_chunk_id, which is NULL for an unresolved edge — an unfiltered recursion tried to recurse into NULL as if it were a real chunk id. The callers direction didn't need the equivalent filter, because its join condition makes NULL naturally fail to match — which made it easy to assume the same safety carried over to the other direction without checking. It didn't.

Verification: 40 new tests, 179 total green. Both implementations agree exactly — on a deliberately cyclic fixture, a diamond-shaped one, one with unresolved edges mixed in, under max_nodes truncation, and on the real Flask call graph in both directions starting from the same ambiguous method Phase 6's resolution heuristic had to disambiguate. A test run that appeared to hang for over 180 seconds turned out to be an unrelated network stall, not a termination bug — see War Stories.

Phase 8 — Hybrid retrieval and fusion Done

Three independently-ranked candidate lists per query — dense cosine similarity, ts_rank full-text, and an exact match against symbol_name/qualified_name — combined by Reciprocal Rank Fusion into HybridStrategy. HybridGraphStrategy wraps it and walks Phase 7's traversal outward from every primary result, both directions, to pull in call-graph neighbors the fused ranking alone wouldn't have surfaced. get_strategy() now constructs real instances for all three modes instead of raising — the interface built in Phase 5 finally has its other two implementations.

The hand-built fixture passed. The real repo didn't.

Every unit and small-fixture integration test was green before this was ever run against Flask. Running it anyway — the same discipline applied in every phase so far — surfaced two real bugs a five-function synthetic repo was structurally too small to expose. First: the query "how does Flask dispatch a request to a view function?" contains the bare word "Flask", which is also the real symbol_name of Flask's entire 1500-line class definition. An unfiltered exact-symbol component matched it, and that giant, barely-relevant chunk outranked the actual answer (Flask.dispatch_request) in the fused result. Second, fixing that surfaced a subtler issue in HybridGraphStrategy's own bookkeeping: chunks already sitting in a component's candidate pool (just below the fused top-k cutoff) were being silently dropped from graph expansion's output entirely, rather than correctly relabeled. Both are written up in Decisions and War Stories below, since the fixes and the reasoning behind them are more interesting than the phase's original plan.

Verification: 24 new tests, 217 total green, including a dedicated regression class against the real Flask fixture (TestFlaskFixtureHybridRetrieval) that pins both fixes down by name so neither can silently regress. All three strategies verified runnable against the same question via codeqa ask with CODEQA_RETRIEVAL_STRATEGY swapped, and hybrid_graph confirmed to recover Flask.dispatch_request — labeled "graph+vector", not bare "graph", since vector search's own candidate pool had already found it too, just not highly enough to survive into hybrid's fused top-k.

Phase 9 — Evaluation harness Done

25 hand-labeled Flask questions, each with a gold set of (file, symbol) pairs a correct answer would have to cite. evals/runners/retrieval_eval.py runs all three strategies against every question via the same get_strategy() path production code uses, and scores each result against its gold set with plain precision/recall — no model, no judge, just set overlap. This is the phase that either earns the project's central claim or doesn't, and it was moved ahead of the agent layer specifically so the answer would exist while there was still time to act on it.

The obvious metric turned out to be blind to the thing being measured

HybridGraphStrategy.retrieve() returns primary + expanded, where primary is exactly HybridStrategy's own fused top-k, unchanged. Computed the conventional way, precision@k/recall@k for hybrid_graph is therefore numerically identical to hybrid's — always, by construction, regardless of whether graph expansion helped at all. Graph-expanded chunks live entirely past the k cutoff; a fixed-k metric structurally cannot see them. Caught before it produced a misleading "graph expansion changes nothing" result: a second metric — recall over hybrid_graph's full returned list, primary plus expansion — was added specifically to see past that cutoff. The fixed-k row is still printed, with a note that the identity is expected, not an absence worth hiding.

Avoiding a circularity trap in the labeled set

Picking gold chunks for multi-hop questions by walking call_edges — grabbing whatever's graph-connected to a plausible starting point — would only prove traversal finds what traversal finds. Phase 7's differential test already proved traversal works; measuring that twice would look like new evidence while being none. Every question's gold set was instead written by reading Flask's actual source and deciding, independently, what a complete and correct answer would have to cite. call_edges was consulted only afterward, to check whether the gold sets turned out to be graph-adjacent — an observation about the result, not an input to building it.

Results: 12 new tests, 229 total green. The honest headline: hybrid's lexical+symbol fusion measured zero recall improvement over naive dense search alone — tied on every single question, not just on average. All of the measured lift came from call-graph expansion, concentrated exactly where the project's thesis predicts: 20 of 25 questions are single-function lookups where naive already hits 100% recall (a ceiling — nothing left to win), and the other 5 are multi-hop questions where naive and hybrid stall at 33–50% recall and hybrid_graph recovers 100%. Of the gold chunks graph expansion alone recovered, 4 of 9 were found by no other mechanism at any rank — not a near-miss, genuinely inaccessible without walking the graph. Full numbers and discussion are in the README's "Retrieval quality" section, including the honest cost: hybrid_graph returns more than double the chunks (22.6 vs 10 average), which is lower precision and more context for an LLM to read per answer.

Phase 10 — Multi-agent pipeline Done

A StateGraph (Pydantic state, verified interactively that a plain stdlib dataclass like RetrievedChunk works directly as a Pydantic field type) with three nodes: locate reruns the configured retrieval strategy (unchanged from Phase 8) against a possibly-refined query; trace asks the LLM a small, non-streaming sufficiency question and parses a two-keyword verdict; synthesize reuses Phase 5's synthesize() unchanged. The one real cycle: if trace says INSUFFICIENT, route back to locate with a refined query, bounded by agent_max_attempts.

Preserving a streaming contract that a state graph doesn't hand you for free

A LangGraph node returns one state update, not a sequence of them — the natural shape for synthesize's node would flatten Phase 5's token-by-token generator into a single blocking call, silently contradicting synthesize()'s own docstring, written back in Phase 5, promising this node would stream. Verified interactively before committing to a design: langgraph.config.get_stream_writer() lets a node emit custom events mid-execution, consumed via graph.stream(state, stream_mode="custom") from outside — confirmed with a throwaway two-node graph before wiring it into the real synthesize node, the same "prove the mechanism in isolation first" discipline used for LangGraph's Pydantic-state and conditional-edge support earlier in this same phase.

The first real run's own output was the tell, twice

Every unit and integration test was green — including one specifically designed to prove the retry edge fires, not just exists — before running codeqa ask --agent against real Flask with a forced retry. Reading that one real run's actual printed output surfaced two things no test had: the refined query's second locate attempt added three chunks — DispatchingJinjaLoader, a duplicate View.view, FormDataRoutingRedirect — none of them more relevant than what attempt 1 already had via hybrid_graph's own call-graph expansion; and the Retrieved: list itself was out of order, a second attempt's real-scored chunks printing after the first attempt's 0.000-sentinel graph-expanded ones. Neither was caught by the test suite, because no test asserted on retrieval quality after a retry or on printed order — both are documented in Decisions and War Stories, since chasing down what the real output actually showed is more informative than the phase's original plan.

Results: 21 new tests, 253 total green. Verified end to end against real Flask with a genuine retry (25 → 28 accumulated chunks). Measured, not assumed: under naive/hybrid the retry is a real recall win (0.25→0.38, 0.12→0.38 on Phase 9's request-lifecycle gold set); under hybrid_graph it's redundant — attempt 1 already sits at the recall ceiling via call-graph expansion alone, so the retry only adds noise (precision 0.32→0.29). Kept the edge anyway: a repo where bounded expansion doesn't reach far enough is exactly where it would still help.

Phase 11 — Citation grounding Done

grounding.py — find_citations, is_grounded, ground_answer, all pure, no LLM, no database. synthesize()'s system prompt has asked the model to cite honestly since Phase 5; nothing before this phase checked that a citation it produced pointed anywhere real. The check itself collapses to one containment test — see "One containment check does the whole grounding job" in Decisions — because a retrieved chunk's own line numbers are already ground truth, so a claimed range contained inside one is automatically real.

Streaming was already live before grounding could run

Both codeqa ask paths stream tokens to the terminal as they arrive — Phase 10's synthesize_node in particular does this through a LangGraph custom writer channel that was verified and tested to work that way in Phase 10. ground_answer needs the complete answer text to check a citation, which means by the time it can run, any ungrounded citation the model produced has already been shown. Rather than quietly claim a suppression that terminal output makes impossible, the CLI prints a clear post-stream warning naming exactly which citations didn't check out — see "Grounding vs. live streaming" in Decisions for the full reasoning, including what a genuinely pre-render-safe version would cost on a future streaming API.

Results: 16 new unit tests (exact match, a narrower sub-range within a real chunk, wrong file, a range extending past a chunk's real boundary, an inverted range, and the fabricated-line-range case the phase's own "done when" bar names explicitly) plus 2 new end-to-end CLI tests proving a fabricated citation in a mocked LLM response is actually flagged through the real codeqa ask wiring — both the direct path and --agent — not just at the unit level. 271 tests green.

Phase 12 — Ingestion and the job worker Done

Everything up to this phase indexed a repo the CLI already had checked out locally. "Any repo, safely" means the server can fetch one itself from a URL a user supplies — which introduces a risk nothing before this phase had: fetching, not just parsing, untrusted input. indexing/clone.py splits that into an SSRF guard (validate_clone_url — see "SSRF guard: an allowlist, not DNS resolution" in Decisions) and the actual clone mechanics (clone_repo — --depth 1, a subprocess timeout, a post-clone size check since git has no pre-clone size guarantee to enforce). indexing/jobs.py is the queue itself, built directly on the index_jobs table Phase 1 already shipped: FOR UPDATE SKIP LOCKED claiming, a heartbeat, and reclaim_stale_jobs — the literal mechanism behind "the job survives a worker restart."

Two config fields from Phase 0 turned out to already anticipate this phase

config.py's scaffold already had clone_max_mb, clone_timeout_seconds, and allowed_clone_hosts sitting unused since Phase 0 — including the exact allowlist (github.com, gitlab.com, bitbucket.org) this phase's SSRF guard needed. Worth noticing before designing a guard from scratch: the simpler, more auditable allowlist approach was already the implied design, not something invented mid-phase.

Results: 39 new tests, 310 total green. indexing/clone.py, jobs.py, and worker.py; the first real routes in api/ (POST /v1/repos, GET /v1/repos/{slug}/jobs/{job_id}); a codeqa worker CLI command. Verified for real, not only against local fixtures: a genuine public GitHub repo (octocat/Hello-World) cloned, indexed, and marked ready with its real HEAD SHA recorded, through both safe_clone directly and the full register→enqueue→process_one_job path — the phase's literal "done when" bar. Worker-restart survival is tested the same way a claim is proven, not assumed: claim a job, force its heartbeat stale, reclaim it back to queued, then confirm a fresh process_one_job call — simulating a different worker process — completes it.

Phase 13 — Incremental re-indexing Done

Every prior phase re-embedded a whole repo on every index, correct but wasteful once a repo is already indexed and only one file changes. indexing/incremental.py makes that case cheap through two diffs at two granularities, both keyed on content hashes rather than a changed-path list from anywhere: file-level (current blob_sha against files.blob_sha already stored) decides which files are unchanged, changed, added, or removed; chunk-level, within a changed file, (content_sha against that file's existing chunks) decides which of its own definitions are genuinely new content versus byte-identical to before. A sibling definition that didn't change keeps its exact chunk_id — see "Incremental diffing compares content hashes against Postgres, not two git commits" in Decisions for why this needed no git history at all, sidestepping a real problem with Phase 12's shallow clones rather than working around it.

The call graph question the plan asked for turned out to have a clean answer

"What happens to call edges pointing at deleted chunks" sounds like it needs careful incremental bookkeeping — track which edges go stale, patch just those. It doesn't, because resolve_and_persist (Phase 6) already deletes and rebuilds a repo's entire edge set on every call. Re-extracting call sites from every currently-present file on every incremental run and letting that existing full-rebuild machinery run normally means there's no dangling-edge state to ever reason about — the honest cost is that graph rebuild isn't itself incremental (it scales with repo size, not change size), accepted because tree-sitter parsing is cheap relative to embedding. See "The call graph is rebuilt fresh every run" in Decisions.

Wired into codeqa index --reindex and the worker's kind="incremental" jobs. Phase 14b — Auth, rate limiting, cache, and degradation Done

The rest of Phase 14's goal bullets, built as their own pass once 14a had proven the bar it was actually scoped to. api/auth.py issues SHA-256-hashed API keys over the api_keys schema that had existed unused since Phase 0's migration — plaintext shown exactly once, at codeqa keys create time, never persisted. api/rate_limit.py's RateLimiter is a Redis token bucket run as a single Lua EVAL script, so the read-refill-consume-write sequence is atomic against two concurrent requests for the same key — a plain Python GET-then-SET would race them into both reading the same starting token count. api/cache.py's QueryCache keys on (repo_id, normalized_question, last_indexed_sha): repo scope alone collides two different repos asked the same question, and question text alone collides a question against stale content after a re-index — the sha in the key makes a re-index a natural cache bust with no invalidation logic required.

A 429 can't be an SSE event — it has to happen before the stream starts

Once EventSourceResponse sends its first byte, the HTTP response is committed to 200; there's no way to change the status code mid-stream. That's why /v1/query's rate-limit check runs in the route function itself, before the cache lookup and before the streaming generator is ever constructed — a rate-limited client needs the real 429 its retry/backoff logic checks for, not a 200 stream carrying an "error" event that looks, at the transport level, exactly like success.

Both Redis integrations fail open, and the cost of that is stated, not hidden

A Redis outage degrades /v1/query to unmetered, uncached traffic — never a 503. For a Q&A service, availability is worth more than strict abuse enforcement, but the honest tradeoff is real: a Redis outage genuinely removes rate-limit protection for as long as it lasts. Measured, not reasoned

A vector search that returned nothing while the data was right there

Symptom
A repo-scoped nearest-neighbour query returned zero rows despite 500 valid matches in the table. No error, no warning — a successful query returning an empty set.
Setup
30,500 vectors across three repos; the target repo held only 500 of them, and they were the farthest from the query. Asked for the 10 nearest chunks in that repo.
Root cause
HNSW is an approximate index. Postgres searches the index first and applies WHERE repo_id = N afterwards. The nearest neighbours all belonged to other repos, so they were found, then filtered away, leaving nothing. Classic ANN filtered-search failure.
Measured
ConfigurationRows returned
Unpartitioned, ef_search=40 (default)0
Unpartitioned, iterative_scan=relaxed_order0
Unpartitioned, + scan_mem_multiplier=410
Unpartitioned, ef_search=100010
Partitioned by repo_id, defaults10
Fix
Partition chunks BY LIST (repo_id). Partition pruning means the scanned partition contains only matching rows — there is no post-filtering step, so there is no recall to lose. Correct at default settings.
Lesson
Every other row in that table is tuning — spend more search effort until the filter probably finds enough. Partitioning removes the failure mode instead of making it less likely. Prefer fixes that change what's possible over fixes that change what's probable.
The obvious fix didn't work

pgvector's purpose-built feature for this didn't fix it

Expectation
hnsw.iterative_scan, added in pgvector 0.8, exists precisely for filtered search — it keeps fetching candidates until enough rows survive the filter.
Symptom
Still zero rows. Raising hnsw.max_scan_tuples from 20,000 to 40,000 — past the full 30,500-row table — changed nothing.
Investigation
Swept both budget knobs independently. max_scan_tuples alone never helped; adding scan_mem_multiplier=4 immediately returned all 10.
Root cause
relaxed_order buffers candidate tuples in memory bounded by work_mem × scan_mem_multiplier. The buffer filled long before the scan reached the target repo's rows. Memory was the binding constraint, not the tuple budget — so the knob that looked relevant was the wrong one.
Lesson
Two knobs that both look like "scan further" can bind differently, and the documentation-obvious one wasn't it. This is the concrete reason the project verifies behaviour against a real database instead of reasoning from API names.
The database suggested the wrong fix

A hint that would have silently disarmed a database-wide guarantee

Symptom
After adding composite foreign keys, dropping a repo's partition failed: cannot drop table chunks_repo_2 because other objects depend on it. Postgres helpfully suggested DROP … CASCADE.
Why the hint is a trap
Those FK constraints are defined on the parent tables — symbols and call_edges — and shared by every repo. CASCADE drops the constraints themselves. Deleting one repo would have quietly removed the cross-repo guarantee for the entire database, and nothing would have failed at the time.
Fix
Delete the dependent rows for that repo, then DETACH PARTITION, then DROP TABLE. Verified that Postgres validates the FKs on detach and refuses to strand rows — tested by trying it with dependents still present and confirming it errors.
Lesson
An error hint optimizes for making the current statement succeed, not for preserving your invariants. Two fixes that were individually correct — partitioning and composite FKs — interacted in a way neither anticipated, and only running the teardown path revealed it.
Subtle by design

Checksum the template or the rendered SQL?

Context
Migrations contain ${EMBEDDING_DIM}, substituted from config, because pgvector needs a fixed dimension at DDL time while the embedding model is configurable.
The question
Drift detection hashes migration files. Hash the raw template, or the SQL actually executed?
Decision
The raw template. Substituted values legitimately differ between environments — dev on 384, prod on 768. Hashing rendered SQL would flag every environment difference as tampering, and an alarm that fires on normal operation is an alarm you learn to ignore.
Consequence
The dimension is then unguarded by the checksum, so it needs its own check: read the deployed column type via format_type and refuse to boot on mismatch. Vectors from different models still produce well-formed similarity scores — they're just meaningless, and every downstream eval number inherits the corruption.
Lesson
"The file is immutable, the config may vary" is the actual invariant. Getting the checksum boundary wrong would have produced either false alarms or a silent gap.

A segfault that only appeared when two test files ran together

Symptom
Fatal Python error: Segmentation fault, deep inside a compiled tree-sitter grammar binding — not a Python exception, not a failing assertion. It surfaced running the full suite: 26 tests passed, then the interpreter died outright.
First, ruling out my own code
Reproduced the exact same sequence of calls — chunk_file and extract_tags across seven languages, then detect_language — in a plain script with no pytest involved. Ran cleanly, every time. Whatever was wrong was not in chunker.py or registry.py; it was something about how pytest itself exercised the same code.
Narrowing it down
Bisected file combinations rather than guessing: test_chunker.py then test_languages.py crashed reliably; the reverse order didn't crash at all. Most likely a native memory bug in a compiled tree-sitter wheel not yet hardened against Python 3.14.2 — a very recent release. Root-causing it looked like it would mean debugging a .so with lldb, so it was recorded as an open question and the verified mitigation shipped.

Pinning below it removed the crash entirely, and the pytest-xdist workaround here was deleted — it was treating a symptom, and it was measurably ~2x slower.
Lesson
A crash that doesn't reproduce in isolation isn't automatically "not a real bug" — the standalone-script test wasn't the end of the investigation, it was the evidence that pointed the search at process-level state rather than my code. But the honest lesson is the one the next story teaches: a mitigation that works is not the same as a diagnosis, and it's worth going back for the real cause when the symptom recurs.

Silent, not loud — the dangerous kind

The answer said "List" and meant "List[str]"

Context
Streaming the LLM's answer to the terminal via rich.Console.print(token, end=""), one small fragment at a time — the same pattern that will back Phase 14's SSE endpoint.
Symptom
No crash, no exception, exit code 0. The first live-ish run (LLM mocked, since no API key is available in this environment) produced an answer that looked complete and readable. Nothing about it looked wrong.
How it was actually found
Not by noticing broken output — by testing the print path in isolation before trusting it, the same discipline applied everywhere else in this project. A one-line check: Console().print("List[str]") renders as List. Rich treats [...] as markup syntax by default, and silently drops anything it doesn't recognize as a valid tag.
Why this one is worse than a crash
A crash stops the demo. This corrupts the answer while looking entirely normal — and an LLM answering questions about code will routinely produce exactly the text that triggers it: list[str], dict[str, Any], chunks[0]. For a project whose central claim is grounded, trustworthy citations, silently mutilating the model's own words is the specific failure mode that matters most to rule out.
Fix
console.print(token, end="", markup=False, highlight=False) on the streamed answer tokens only — the CLI's own styled output (citations, scores) keeps markup enabled deliberately, since that styling is intentional.
Lesson
The dangerous bugs in an LLM-output pipeline are the ones with no error signal at all. Every place this project prints or renders model-generated text is a candidate for the same class of bug, and each one needs the same one-line check before being trusted — not assumed safe because the library "just prints strings."
The plan's own success criterion was wrong

The 3-hop chain that couldn't exist

Context
Phase 6's own stated "done when" bar, written back at design time: get Flask.full_dispatch_request → Flask.dispatch_request → view into call_edges. A specific, checkable target — which is exactly why it was worth checking against the real source before building the extraction logic around it.
What reading the actual line showed
return self.ensure_sync(self.view_functions[rule.endpoint])(**view_args)
The view isn't called by name. It's looked up at runtime from a dict (view_functions[rule.endpoint]), wrapped by another call (ensure_sync(...)), and the result of that is what gets invoked. tree-sitter's call-reference query matches a call whose function is a plain identifier or attribute access — a call-expression standing in as the function is a different shape entirely, and it doesn't match.
Verified, not assumed
Extracted tags from that exact line before writing a single word of the extraction module. Result: ensure_sync is captured as a call reference; nothing named "view" is. That's not an implementation gap to fix later — there is no symbolic name for tree-sitter to have captured. The dispatch target only exists as a runtime value.
What this meant for the phase
The literal 3-hop bar as written is unachievable by any syntactic approach, including a more sophisticated one. Rather than force a workaround or quietly redefine "done" without saying so, the bar was corrected in the plan document itself, with the reasoning attached: the achievable 2-hop chain became the actual verification target, and the third hop's absence became an asserted, tested fact (test_the_dynamic_view_dispatch_is_not_captured) instead of a silent gap someone would eventually notice and wonder about.
The upside
The 2-hop chain that remained turned out to be a better test than the original 3-hop one would have been. dispatch_request is defined on three different classes in real Flask, so resolving full_dispatch_request's call to it correctly requires the same-class heuristic to do real work — a single unambiguous target would have proven nothing about disambiguation at all.
Lesson
A written spec is a hypothesis, not a guarantee — including one written earlier in the same project, by the same reasoning that produced everything else. The discipline that catches a wrong dependency claim or a wrong library assumption applies exactly as well to a target the plan itself set. Checking it costs one grep-sized detour; not checking it costs building the wrong thing and finding out from a failing "done when" bar at the end.
The one phase where a hang would have looked like the answer

A network stall in the middle of the termination phase

Context
Phase 7's entire subject is proving traversal terminates on a cyclic graph. Running the full test suite after finishing it, the process sat for over 180 seconds with zero output — in any other phase, a slow test. Here, it was the single worst possible moment for something to look like it might not terminate.
What it was tempting to assume
That a cycle had slipped past the CYCLE clause or the visited-set logic somewhere, and something was spinning. The traversal code was the newest, most directly relevant suspect in the room.
What was checked instead of assumed
Three quick, ordered checks, each one ruling out a specific hypothesis rather than guessing at a fix:
  • pg_stat_activity on the actual Postgres connection — state=idle, wait_event_type=Client, sitting on a completed COMMIT. The server was not blocked on a query; it was waiting for the client to say anything at all.

Root cause
Sentence-transformers checks Hugging Face Hub for a fresher version of the model on construction, even when a valid local copy is already cached. That network call stalled. Nothing about the call graph, the CYCLE clause, or the differential test was involved.
Fix, deliberately narrow
HF_HUB_OFFLINE=1 makes it skip the check and use the cache directly — confirmed working in under a second once set. Not added to test configuration or CI defaults: forcing offline mode unconditionally would make a fresh checkout with no cached model fail outright instead of slowly succeeding, trading a slow first run for a broken one. Documented as local guidance instead, for once the cache already exists.
Lesson
The context of a bug shapes which explanation feels obvious, and that pull is exactly when a stepwise elimination check matters most — a hang during the termination phase reads as a termination bug until you've actually looked, and looking took three commands and about a minute against a "just add a timeout and move on" instinct that would have proven nothing about whether the code was actually correct.

Filtering symbol matches fixed one bug and briefly caused a worse one

Context
Every hybrid-retrieval test — unit tests, a purpose-built four-file fixture repo — was green before running the same query against real Flask: "how does Flask dispatch a request to a view function?"
Symptom
Hybrid's top result was the entire Flask class — 1500-plus lines, one chunk — not Flask.dispatch_request. The word "Flask" in the query is also that class's exact symbol_name, and the unfiltered symbol component let that match win in fusion.
First fix, and what it broke
Added shape-based filtering (filter_symbol_candidates) so ordinary words like "Flask" stop qualifying as symbol candidates — correct, and confirmed the giant class chunk no longer won a bare match. But the same investigation had also produced a second change: excluding any chunk already present in any component's candidate pool from graph expansion, on the reasoning that vector/lexical/symbol search "already found it" so graph shouldn't take credit. "Hybrid changes nothing" — plausible, and close to what got reported to the user at first. TestClient passed clean; real uvicorn did not

OTel spans need an explicit parent across a thread pool

Symptom
The very first version of /v1/query wrapped the whole SSE generator in with tracer.start_as_current_span("query"):. Against a real running uvicorn server, every query crashed with a logged OTel warning: "Failed to detach context" / ValueError: Token ... was created in a different Context. Against FastAPI's TestClient, the identical code ran clean — zero reproductions.
Root cause
sse-starlette's EventSourceResponse wraps a plain sync generator and starlette drives it via iterate_in_threadpool, which dispatches each next() call independently through anyio.to_thread.run_sync — nothing guarantees two consecutive calls land on the same OS thread. OTel's attach()/detach() hand out a contextvars.Token that is only valid to reset on the thread that created it. A span held open across a yield attaches on whichever thread ran the first call and gets detached on whichever thread happens to run a much later one — a mismatch the instant the thread pool reuses a worker. TestClient's ASGI transport doesn't reproduce this because it doesn't exercise the same real thread-pool concurrency a live server does.
The obvious-looking fix that was still wrong
Narrowing the attach()/detach() window to wrap only each individual next() call stopped the crash. But inspecting the resulting traces in Jaeger directly showed a second, quieter problem: on one run, the trace span was parented directly under the HTTP request span instead of under the intended query span — ambient context propagation across this boundary is unreliable, not merely occasionally slow to raise.
Fix
Stop relying on ambient "current span" state entirely. agents/nodes.py's node factories take an explicit parent_context parameter and pass it as context= to their own start_as_current_span calls. Each node's span still opens and closes within one synchronous call on one thread — self-contained regardless of which thread happens to run it, with no dependency on an outer wrapper having set anything up first.
Verified
Not just "no exception raised" — queried Jaeger's own HTTP API directly and checked span parent IDs in the response: locate and trace both correctly nested under query, itself nested under the FastAPI-instrumented request span, on every run after the fix.
Lesson
A test harness that doesn't reproduce a target environment's concurrency model can pass clean on a bug that only exists under real concurrency. And a fix that merely stops the crash isn't automatically the fix that produces correct behavior — the wrong-parent trace only surfaced by looking at the actual trace data, not by the absence of an error.

On retrieval

Why Postgres with pgvector instead of a dedicated vector database?

Hybrid retrieval needs dense vectors, full-text ranking and an exact symbol index combined. In one database that's a join. Across two systems it's a client-side merge with two sets of credentials, two failure modes and a consistency problem when indexing writes to one and not the other.

The call graph also has to live somewhere transactional next to the chunks, and the traversal is a recursive CTE over those edges. Splitting vectors out would leave the majority of the interesting queries in Postgres anyway. At this scale a dedicated vector DB buys throughput I don't need at the cost of an integration I'd have to maintain.

What does HNSW actually give up compared to exact search?

Recall. Exact search compares the query against every vector — perfect results, cost linear in table size. HNSW builds a multi-layer navigable graph and walks it greedily, which is dramatically faster and will sometimes miss a true top-k neighbour. m controls graph connectivity; ef_construction controls build-time search width; ef_search controls query-time width. Higher means better recall, slower builds, more memory.

The failure that actually bit me wasn't ordinary recall loss — it was the interaction with filtering, where approximate search plus a post-applied WHERE can return nothing at all.

Why is hybrid retrieval worth the complexity over dense-only?

Because code is full of identifiers, and identifiers are lexical rather than semantic. Ask "where is dispatch_request defined" and a pure embedding search returns functions that feel like request dispatching — semantically close, exactly wrong. Full-text search and an exact symbol index catch what embeddings blur, and RRF fuses the ranked lists without needing their scores to be comparable.

How does RRF work, and why not just weight the scores?

RRF scores each document as Σ 1/(k + rank) summed across result lists, where k is a damping constant (60 is conventional). It consumes ranks, not scores.

That's the point. Cosine similarity lives roughly in [-1, 1]; Postgres ts_rank has no fixed range. Weighting them requires constants with no principled basis that you'd retune whenever either component changed. Ranks are comparable by construction.

Why filter symbol candidates by token shape instead of a stopword list?

Found running hybrid retrieval against the real Flask repo, not the small hand-built fixture: ordinary English words in a question are frequently also real symbol names. "Flask", "view", and "request" are a class and two methods in Flask's own source. Unfiltered, the entire 1500-line Flask class chunk won an exact bare-symbol match and outranked the actual answer in fusion.

A stopword list can't fix this — it can't tell "Flask" the class from "flask" the container, and it needs constant upkeep as new false positives turn up in new repos. Token shape can: an underscore or an internal capital letter (dispatch_request, SessionManager) is real evidence a token is meant as an identifier; plain lowercase English words aren't. The cost is a real symbol name that's a single lowercase word losing its exact-match boost — accepted, since there's no shape-based way to tell that from an ordinary word, and false positives from common words are the worse failure of the two.

What exactly does a chunk's source field mean, and why does the exact string matter?

It records which mechanism(s) produced a chunk: any combination of "vector", "lexical", "symbol" joined with +, or "graph" — optionally also joined with one of the other three, when call-graph expansion surfaced a chunk that some component's candidate pool had also touched without it surviving that component's own fusion into top-k.

The exact string matters because Phase 9's eval reads source == "graph" literally to mean "no other mechanism came close" — the central measurement this project exists to make. An earlier version conflated "another component's pool touched this" with "exclude it from graph expansion entirely," which silently dropped a correct answer (Flask.dispatch_request) from the results. The fix keeps expansion inclusive and puts the precision in the label instead: "graph" alone versus "graph+vector" are different, honest claims, and only the first one is evidence the call graph found something nothing else would have.

On evaluation

Your eval says hybrid adds nothing. Why keep it at all?

Two separate reasons, and I try not to blur them. First: the eval's 25 questions are all natural-language paraphrases — I deliberately avoided putting literal identifiers in the query text, and hybrid's exact-symbol component is specifically for the case where a question does contain one ("where is dispatch_request defined"). None of my questions ask that way, so the eval never exercised the path hybrid exists for. That's a gap in the eval, not evidence hybrid is dead weight — "unproven" and "disproven" are different claims and I only have grounds for the first.

Second, independent of that: naive stays permanently selectable as an invariant regardless of what any single eval run shows, because it's the baseline the entire comparison is measured against — deleting it the moment it "wins" a measurement would quietly end the ability to make that comparison ever again.

Why does hybrid_graph's precision@k table row look identical to hybrid's?

Because it is, by construction — not a bug, and not a coincidence. HybridGraphStrategy.retrieve() returns primary + expanded, where primary is exactly HybridStrategy's own fused top-k, byte-for-byte unchanged. Any metric computed over just the first k results is computed over that identical primary list, so it can't differ. Graph-expanded chunks live entirely past that cutoff — which is exactly why a second metric exists: recall over the strategy's full returned list, the only one that can see what expansion actually contributed.

How do you know your labeled set isn't just measuring your own traversal code?

By not building the gold sets from the call graph in the first place. It would have been easy — for a multi-hop question, walk call_edges from a plausible starting point and use whatever's reachable as the gold set. That measures "does traversal find what traversal finds," which Phase 7's differential test against a real networkx implementation already settled. Instead, every gold set was written by reading Flask's actual source and deciding independently what a complete answer would have to cite; call_edges was consulted only afterward, to observe whether the gold sets turned out to be graph-adjacent — which most of them did, but as a finding, not a filter I built in.

On the call graph

What happens if a query hits a function that calls into a cycle?

Traversal is bounded on two axes: a maximum depth, and cycle detection. Postgres has a CYCLE clause on recursive CTEs that maintains the visited path and marks a row when it revisits a node, so traversal terminates on cyclic graphs natively rather than by hand-rolled bookkeeping.

It's tested against a deliberately cyclic fixture, and against a networkx BFS implementation that must produce identical output — differential testing rather than trusting one implementation.

How accurate is your call graph, really?

It's syntactic, and I'd rather say that plainly than oversell it. Tag queries see a call site named foo; resolving which foo is genuinely hard in a dynamic language. There's no type inference and no dynamic-dispatch resolution, so self.handler() often can't be pinned to one target.

So every edge carries a resolution class — exact, approximate, or unresolved — and the raw callee name is kept alongside it. Approximate edges are never presented as certain call paths. The honest claim is "high-value approximation with stated limits", not "static analysis".

Why not a graph database for the call graph?

The workload is bounded-depth traversal from a small seed set — three or four hops, not arbitrary pattern matching. Postgres does that in a recursive CTE with built-in cycle detection. A graph database would be a second system to run, sync and fail independently, and the edges still need to sit transactionally beside the chunks they reference.

If the workload became global graph analytics — centrality, community detection — that calculus changes. It hasn't.

On the agents

Why LangGraph? Isn't this just three function calls?

For a purely linear locate → trace → synthesize pipeline, that criticism is fair and I'd concede it. What earns the dependency is the conditional edge: when trace finds insufficient context, the graph routes back to locate to re-query with refined terms, bounded by an attempt counter in shared state.

That needs conditional routing over accumulated state, which is exactly what a state graph provides. Worth noting the original design justified LangGraph with "support for cycles" while the cycles were in the call graph, not the agent graph — I caught that conflation and added a real cycle rather than leave the justification hollow.

And it's not just wired in — it's proven to fire. The integration test mocks two different trace verdicts in sequence (INSUFFICIENT then SUFFICIENT) and asserts locate actually ran twice, not just that the edge exists in the compiled graph.

Does the retry loop actually help?

Measured, not assumed, and the honest answer is "it depends which retrieval strategy is underneath it." Ran the same real Flask question through the retry mechanism under all three strategies and scored recall on Phase 9's request-lifecycle gold set before and after. Under naive/hybrid it's a genuine recall win (0.25→0.38, 0.12→0.38). Under hybrid_graph, attempt 1 already hits the recall ceiling via call-graph expansion alone, so the retry can only add noise — precision measurably drops (0.32→0.29).

The retry loop and call-graph expansion are two different mechanisms for the same underlying gap: a single query embedding can't reach every relevant chunk in a multi-hop flow. Whichever one runs first captures most of the available gain, which is why the second one looks redundant on the same question rather than additive. Kept the edge anyway — a repo where bounded expansion doesn't reach far enough is exactly the case it would still help on.

How does the final answer still stream token by token through a state graph?

A LangGraph node normally returns one state update, which would naturally flatten Phase 5's token-by-token generator into a single blocking call — exactly the kind of quiet regression that's easy to miss since the pipeline would still "work," just without streaming. langgraph.config.get_stream_writer() lets a node emit custom events mid-execution instead of waiting to return; a caller using graph.stream(state, stream_mode="custom") receives them as they're written. Verified with a throwaway two-node graph before trusting the design, then wired into the real synthesize node unchanged from how Phase 5 built it.

What stops the model from inventing a citation?

Grounding is a deterministic function (grounding.py), not a prompt instruction. Every claimed citation is checked with a single containment test: does some chunk actually in context have that exact file, with its real start_line/end_line containing the claimed range? A chunk's own bounds are already ground truth from tree-sitter's real parse, so that one check covers file existence and range existence at once. 16 unit tests cover accept and reject paths, including a fabricated line range.

Whether a bad citation is dropped before render depends on the caller, and it's worth being precise here rather than overclaiming: ground_answer's own return value never contains a raw ungrounded citation, so a non-streaming caller shows only clean text. But both codeqa ask paths stream tokens live to the terminal before the full answer exists to check — grounding can't run until the last token arrives. So today the CLI flags what was dropped after the stream finishes rather than literally suppressing it beforehand, which is an honest, stated tradeoff, not a gap I'd want to gloss over if asked directly.

The limit worth stating precisely regardless of that: this verifies the citation, not the claim. It proves the cited code exists and was retrieved. It cannot prove the sentence attached to it is a correct description. Faithfulness is measured separately in the eval harness.

On engineering judgment

Walk me through debugging the segfault.

The full test suite died with Fatal Python error: Segmentation fault — not a Python exception, the interpreter itself crashing inside a compiled tree-sitter binding. First move was ruling out my own code rather than guessing at a fix: I reproduced the exact same sequence of calls — chunk_file and extract_tags across seven languages — in a plain script with no pytest involved. Ran cleanly, repeatedly. That told me the bug was in how pytest exercised the code, not in the code itself.

From there I bisected rather than theorized: which combination of test files triggers it, and does order matter? It did — test_chunker.py then test_languages.py crashed reliably, the reverse order never did. That ruled out "too many grammars in one process" immediately, since both orders touch the same eleven grammars. Then I ruled out three specific hypotheses one at a time, each with a fast, decisive check rather than a plausible-sounding guess: a free-threaded Python build (checked directly, not the case), garbage-collection timing (gc.disable(), still crashed), and pytest's assertion rewriting (--assert=plain, still crashed).

What was left pointed at accumulated native state within whichever process ran that specific sequence — confirmed when even pytest-xdist's default load-balanced distribution still crashed a worker that happened to get unlucky ordering. --dist loadfile, which guarantees a file's tests never interleave with another file's in the same process, fixed it — verified across three separate runs before I trusted it.

I did not chase the exact native root cause further. It's almost certainly a memory bug in a compiled grammar wheel not yet hardened against Python 3.14.2, a very recent release at the time — finding the precise line would mean debugging a .so I can't patch even if I found it. The mitigation is verified and real; I recorded the open question rather than pretending it's closed, and flagged that a long-running indexing worker parsing many languages sequentially is the same shape of workload, so it's worth revisiting when that worker gets built.

Why do you need two implementations of traversal instead of just testing the SQL directly?

Because testing the SQL directly against hand-written expected output only catches the gap between the SQL and my own mental model of what it should do — and that mental model was wrong twice in this phase. I assumed CYCLE gave full deduplication; it only prevents a single path from repeating a node. I assumed the NULL-safety I'd verified for one traversal direction applied symmetrically to the other; it didn't. A hand-written expected-output test would have encoded the same wrong assumptions into the test as into the code, and passed.

A second, independently implemented traversal — real networkx, not a second copy of my own loop — can be wrong in different ways than the first one. When they disagree, that's real signal. Both bugs here were found exactly that way: the SQL version returned one result, the networkx version returned a different one, and the disagreement is what sent me back to figure out which one was actually correct — which in both cases was networkx, and the SQL got fixed to match.

Walk me through resolving an ambiguous call.

Concretely: Flask.full_dispatch_request calls self.dispatch_request(ctx). The tag query captures the bare name dispatch_request — no receiver type, since there's no type inference here by design. Real Flask defines that method on three separate classes: Flask, View, MethodView. Naively, that's a three-way tie.

Resolution runs as an ordered set of tie-breakers, and each one only fires if it produces exactly one match. Zero candidates repo-wide means the callee is external — a builtin, a third-party call — and the edge is unresolved. One candidate means there was never any ambiguity, and it's exact. With three candidates like this one, the next tier checks whether exactly one of them is defined on the caller's own class — since full_dispatch_request is itself a method of Flask, and exactly one candidate is Flask.dispatch_request, that's the match. Labeled approximate, not exact — the heuristic could in principle be wrong (inheritance, a same-named unrelated method), so the confidence level says so honestly.

If that tier also failed to narrow it to one, there's a second tier — same file as the caller — and after that, the edge is left unresolved rather than picking one of the remaining candidates arbitrarily. An edge sitting in the database has to be trustworthy enough to walk during retrieval; a confidently wrong one is worse than an honestly missing one.

How do you find bugs that don't crash and don't throw?

By not trusting a rendering or formatting path just because it "just prints strings" — testing it with adversarial input before relying on it, the same discipline used everywhere else in this project. The concrete case: streaming an LLM's answer to the terminal through rich's Console.print(). It ran, it exited 0, the output looked like a normal sentence. It was wrong. Rich parses [...] as markup by default, so Console().print("List[str]") silently renders as List — no error, no warning, just missing text.

That class of bug is worse than a crash specifically for this project. A crash stops the demo; this corrupts the model's own words while looking completely normal, and an LLM answering questions about code will constantly produce exactly the bracket syntax that triggers it — list[int], chunks[0]. For something whose whole claim is trustworthy, grounded citations, silently mutilating the text is the single worst failure mode to leave unrouted. Fixed with markup=False on the streamed tokens specifically, keeping it enabled for the CLI's own deliberately styled output.

How do you decide whether to trust a dependency?

By what it does at runtime combined with what the system does with untrusted input — not by how convenient it is. A bulk grammar-pack library offering 371 languages in one dependency looked like an easy win right up until I read its API and found DownloadManager and download_all: it fetches compiled native binaries over the network at runtime, from a commercial org created a few months earlier, not the canonical tree-sitter maintainers.

That's disqualifying specifically here, because this system clones and parses arbitrary third-party repositories. A dependency that downloads and dynamically loads native code while indexing a stranger's repo reintroduces exactly the supply-chain risk that "tree-sitter parses but never executes" is supposed to rule out. I checked PyPI metadata, the GitHub org's creation date, and the package's actual exported API before deciding — not just the star count. Ten official packages, individually pinned, cost more typing and bought a supply chain I could actually reason about.

How do you know call-graph expansion actually helps?

Because it's measured rather than asserted. There's a labeled set of Flask questions with known-correct files and symbols, and a runner reporting precision@k and recall@k for three strategies: naive dense retrieval, hybrid, and hybrid plus graph expansion.

The naive baseline was built first specifically so there'd be something to measure against, and it's never deleted — it stays config-selectable permanently, so the comparison is reproducible at any commit. The usual way this fails is refactoring the baseline out of existence and losing the ability to reproduce the claim.

Why partition rather than tune ef_search?

Tuning makes the failure less likely; partitioning makes it impossible. With ef_search=1000 the query worked in my test, but that's a number chosen against one data distribution — a repo with a different shape, or more repos, moves the threshold and the failure returns silently.

With one partition per repo, WHERE repo_id = N prunes to a single partition where every row already satisfies the filter. There's no post-filtering step, so there's no recall to lose, at default settings, regardless of distribution.

What did partitioning cost you?

Three things. A partition must be created when a repo is registered, so registration does DDL. The primary key must include the partition key, making it (repo_id, id), so everything referencing chunks uses composite foreign keys. And foreign keys referencing a partitioned table create one catalog constraint entry per partition, so constraint count grows with repo count — fine at tens to hundreds, worth revisiting beyond that.

The composite-FK consequence turned out to be a benefit: a cross-repo edge is now a foreign-key violation. The scoping invariant stopped being something to remember and became something the database enforces.

Your system supports "all languages" — how, realistically?

Through one query-driven code path, not N parsers. Tree-sitter grammars ship queries/tags.scm declaring @definition.function, @definition.class and @reference.call. The extractor runs those queries, so adding a language ships a .scm file rather than code.

Support isn't uniform, and the system declares that rather than hiding it. Tier 1 grammars have both definitions and call references — verified for Python, JavaScript, Go, Java, Rust, Ruby and PHP. TypeScript and C++ ship definitions only, so calls are approximated by symbol name. C# ships no tag queries, so it gets chunks and symbols until someone writes them.

Is it safe to index a repository you don't control?

The core property is that tree-sitter parses but never executes. Indexing untrusted code never runs it — no imports, no build step, no evaluation. That's safe by construction rather than by sandboxing.

The real exposure is the clone, not the parse: a server fetching a user-supplied URL needs an SSRF guard, --depth 1, a size cap, a clone timeout and a disk quota. Those are the controls on the ingestion path.

What's the weakest part of the system?

Call resolution. Everything downstream — trace quality, multi-hop answers, the entire differentiating claim — depends on caller/callee edges being right, and they're derived from syntax without type information. In a dynamic language a meaningful fraction of call sites can't be resolved to a single target.

That's why edges carry a resolution class, why approximations are never presented as certainties, and why per-stage failure attribution is in the eval harness — so a bad answer can be traced to the stage that caused it rather than blamed on "the LLM".

How would you scale this to ten thousand repositories?

The current design would strain in two known places. Partition-per-repo means catalog growth and planning-time cost at that count, so I'd move to hash partitioning with a bounded partition count, accepting some in-partition filtering back — and re-measure the filtered-recall behaviour, since that's exactly the tradeoff being reversed.

The second is indexing throughput: one polling worker doesn't scale, so jobs would need claiming via SELECT … FOR UPDATE SKIP LOCKED across multiple workers. The partial unique index on live jobs already keeps one repo from being indexed twice concurrently, so that part holds.

What would you do differently if you started over?

I'd verify database behaviour before writing schema, not after. The partitioning decision came from measuring a filtered vector search, and that measurement could have happened on day one — instead it revised a schema I'd already written and documented.

More generally: the sequencing lesson from moving evals earlier applies to infrastructure too. Test the assumption you'd most regret being wrong about, first.

Why SSE for /v1/query instead of WebSockets?

The data only flows one direction — server to client, tokens and progress events — and the client never needs to send anything mid- stream. WebSockets buy full duplex; nothing here uses the other direction. SSE is plain HTTP, so it survives the proxies and load balancers a WebSocket upgrade sometimes doesn't, auto-reconnects with a last-event-id in the browser's native EventSource, and needed no new library on the server: sse-starlette was already a pinned dependency waiting for this phase.

The actual mechanism is a plain sync generator — the same locate → trace → synthesize graph codeqa ask --agent already drives in the terminal — wrapped in EventSourceResponse. Starlette's iterate_in_threadpool is what keeps the blocking psycopg and litellm calls inside off the event loop, so nothing in the retrieval or LLM path needed an async rewrite.

Why does agents/nodes.py take an explicit parent_context instead of just using OTel's current-span context?

Because ambient context breaks across the exact concurrency model /v1/query uses. iterate_in_threadpool dispatches every chunk of a streamed response through anyio.to_thread.run_sync independently, with no guarantee two calls share a thread. OTel's attach() / detach() hand out a contextvars.Token valid only on the thread that created it — a span held "current" across a yield attaches on one worker thread and can be asked to detach on a different one the moment the pool reuses a worker. That reproduced as a real crash under live uvicorn and, after a narrower fix, as a real wrong-parent trace — visible only by checking actual span data in Jaeger, not by the absence of an exception. Passing parent_context explicitly into each node's own start_as_current_span call sidesteps ambient state completely: a node's span still opens and closes within one synchronous call on one thread, so it's correct regardless of which thread happens to run it. Full account in War stories.

Known limits

Volunteering these is stronger than being caught by them.

  • Call resolution is syntactic. No type inference, no dynamic dispatch. Some call sites resolve to nothing or to the wrong target; edges are labelled with confidence accordingly.
  • Not multi-tenant. Many repos, no isolation boundary between users. Stated as a scope cut, not an oversight.
  • Partition-per-repo has a ceiling. Catalog constraint entries grow with repo count. Comfortable at tens to hundreds.
  • Grounding verifies citations, not claims. It proves cited code exists and was retrieved, not that the sentence describing it is correct.
  • English text-search config on source code. Stemming identifiers with English rules is a compromise; whether simple does better is a measurable question the eval harness can settle.
  • Tier 2 and 3 languages get degraded call graphs — approximate or absent. Declared per language rather than silently applied.
  • Symbol matching misses single-word, all-lowercase identifiers. Shape-based filtering (an underscore or internal capital required) can't distinguish a real function named e.g. dispatch from the English verb, so it doesn't get the exact-match boost. A deliberate tradeoff against the worse failure — common words polluting matches — not an oversight.
  • Chunk granularity affects lexical recall in a way retrieval can't fix. A whole-class chunk (Flask's Flask class is 1500-plus lines, one chunk) can lexically match many unrelated query terms just by containing them somewhere in its body. Retrieval-layer filtering narrows this; it doesn't eliminate it. A chunking-granularity question, out of this phase's scope.
  • No numbers claimed until measured. No precision@k or latency figure goes in the README or on a résumé before the harness produces it. A modest measured number is defensible; an impressive invented one collapses on the second question.
  • The labeled set is small and single-repo. 25 questions against Flask alone. Real, but not enough to generalize a percentage beyond "the direction of the effect held on the repo tested" — a second anchor repo would be needed before quoting these numbers as broadly predictive.
  • The labeled set never tests hybrid's actual purpose. All 25 questions are natural-language paraphrases with no literal identifiers in the query text — so hybrid's exact-symbol component, built specifically for "where is dispatch_request defined"-style questions, was never exercised. Its measured zero lift is honest for this set and not evidence it's unnecessary in general.
  • No load testing exists at any layer. Every performance-shaped claim in this document (indexing time, traversal query bounds) is architectural reasoning from one mid-size repo (Flask, 446 chunks), not a benchmark. Phase 14a gives the system real tracing to measure with; no load test has actually been run yet to produce a latency number from it.
  • The agent retry loop is measurably redundant with hybrid_graph. It's a real recall win under naive/hybrid but adds only noise once call-graph expansion already recovered everything reachable — two mechanisms for the same gap, and whichever runs first captures most of the benefit. Kept because a repo where bounded expansion doesn't reach far enough is a real, not hypothetical, case it still helps on.
  • Every agent-pipeline test uses a mocked LLM. No live API key exists in this environment (same honesty boundary as Phases 5/8/9). trace's sufficiency judgment has never been exercised against a real model's actual reasoning — only against hand-scripted SUFFICIENT/INSUFFICIENT responses. Whether a real LLM reliably produces the expected two-keyword format, and judges sufficiency well, is untested.
  • Rate limiting and caching fail open. A Redis outage means every request degrades to unmetered, uncached traffic rather than a 503 — a deliberate availability-over-enforcement choice for a Q&A service, but it genuinely removes abuse protection for the outage's duration. Stated as a tradeoff made on purpose, not a gap.
  • A connection is opened per request rather than pooled. psycopg_pool is an installed extra but unused — the simplest thing that works, not optimized ahead of a concurrency number that has never actually been measured.
  • API keys have no expiry. A key is valid until explicitly revoked; there's no TTL or forced rotation. Revocation exists (revoked_at), rotation policy does not.
  • Re-indexing a git_url repo re-clones from scratch. The worker wipes any existing checkout under clone_workdir and clones fresh every time rather than fetching incrementally. Correct, but not the fast path — Phase 13's incremental re-index is what replaces this with a real diff against last_indexed_sha.
  • The SSRF guard is an allowlist, not a general defense. Only github.com/gitlab.com/bitbucket.org can be cloned from out of the box. A self-hosted git server needs its host added to allowed_clone_hosts explicitly — a deliberate default-deny, not a gap, but worth stating precisely rather than implying broader coverage.
  • Incremental re-indexing only makes embedding cheap, not cloning or graph rebuild. A git_url repo still gets a full fresh --depth 1 clone on every incremental run (Phase 12's clone behavior is unchanged), and the call graph is fully re-extracted and rebuilt from every currently-present file every time, not diffed. Only chunk-level embedding is genuinely incremental. Stated precisely because "incremental re-indexing" could otherwise imply more than this phase actually delivers.

Glossary

Terms this project uses that an interviewer may ask you to define cold.

CST
Concrete syntax tree — tree-sitter's output. Unlike an AST it preserves every token including punctuation and comments, which is what makes exact line spans recoverable.
Tag query
An S-expression pattern in tags.scm that captures definitions and references from a parse tree. The uniform mechanism behind multi-language support.
HNSW
Hierarchical Navigable Small World — an approximate nearest-neighbour index built as a layered proximity graph, traversed greedily.
RRF
Reciprocal Rank Fusion — combines ranked lists by Σ 1/(k + rank), using positions rather than scores so incomparable scales don't matter.
Recursive CTE
A self-referencing SQL common table expression. Postgres 14+ adds a CYCLE clause that tracks visited paths, giving cycle-safe graph traversal in one query.
tsvector
Postgres's parsed, normalized full-text representation. Here a generated column, so it can't drift from the content it indexes.
Partition pruning
The planner excluding partitions that can't match a predicate. The mechanism that makes repo-scoped vector search exact rather than approximate-then-filtered.
Token bucket
Rate-limiting scheme where a bucket refills at a steady rate and each request spends a token. Permits bursts up to bucket size, unlike a fixed window.
SSE
Server-Sent Events — one-directional server→client streaming over plain HTTP. Sufficient for token streaming and simpler than WebSockets.
Precision@k
Fraction of the top k results that are relevant. Recall@k is the fraction of all relevant items appearing in the top k.
