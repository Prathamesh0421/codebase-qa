Project reference

Multi-agent RAG over source code

Everything behind CodeQA — what it does, every decision and the alternatives rejected, the problems hit while building it, and the answers to the questions those decisions invite.

Explaining it

Three lengths. Interviews ask for all three, usually in this order.

30 seconds

It answers questions about unfamiliar codebases — "how does auth work here", "what happens between the route handler and the database". Generic RAG chunks source at arbitrary character boundaries and splits functions mid-body. This parses with tree-sitter and chunks at function and class boundaries, so every retrieved unit is syntactically complete. The part I care about: it also extracts the call graph, so when it retrieves a function it pulls in that function's callers and callees. That's what lets it explain a flow instead of a fragment.

Two minutes

Four layers. Indexing parses a repo with tree-sitter, chunks by function/class, extracts caller→callee edges, embeds, and writes to Postgres with pgvector. Retrieval is hybrid — dense vector search fused with Postgres full-text and an exact symbol index via Reciprocal Rank Fusion — then expands along the call graph. Reasoning is a LangGraph state machine: locate → trace → synthesize, where trace walks a cyclic call graph with bounded depth. API is FastAPI with SSE streaming, API-key auth, Redis rate limiting, and OpenTelemetry spans per stage.

The piece I'd point at is the eval harness. The whole premise is that call-graph expansion improves retrieval, so there's a labeled question set and a runner that measures precision@k for naive vs hybrid vs +graph. I built the naive baseline first specifically so there was something to measure against, and I never deleted it.

Five minutes — add the decisions

Then walk the decisions in section 05, and land on one war story from section 07. The HNSW partitioning one is the strongest: it's a real bug, it was found by measurement rather than reasoning, the obvious fix didn't work, and the eventual fix made a whole class of bugs impossible instead of less likely.

Problem & thesis

What's actually hard here, stated so the design reads as a consequence of it.

Engineers joining an unfamiliar codebase spend disproportionate time on structural questions. Answering them requires more than finding a relevant function — it requires knowing how that function connects to the rest of the system: who calls it, what it calls, where it sits in an end-to-end flow.

General-purpose "chat with your documents" RAG handles this badly for code, in two specific ways:

  • Chunking destroys syntax. Fixed character windows split functions mid-body. A chunk containing the back half of one function and the front half of the next is not a meaningful retrieval unit, and an embedding of it means very little.
  • Retrieval is call-graph blind. Even a perfectly retrieved function is an isolated snippet. The model can describe what it does, but not how it participates in a flow — which is precisely the information a new engineer needs.
The thesis

Retrieving a function plus its direct callers and callees produces measurably better retrieval than semantic similarity alone. Everything distinctive about this project follows from that claim — which is why the eval harness that tests it was moved ahead of the agent layer.

Flask is the anchor repo for evaluation because it has genuine multi-hop request flows: route → add_url_rule → full_dispatch_request → dispatch_request → view. "What happens between a request arriving and my view function running" is exactly the question naive RAG fails and call-graph expansion should win. Flatter libraries like requests were rejected as anchors for having too few multi-hop chains to demonstrate anything.

Architecture

Four layers, one database.

Indexing

Enumerate source files → parse with tree-sitter → emit function/class chunks with metadata → extract call edges → embed → upsert into Postgres. Runs as a background job, not in a request: indexing takes minutes.

Storage

One Postgres instance holds vectors (pgvector), chunk metadata, the symbol index, and the call graph. Redis holds the query cache and rate-limit buckets. Using one database rather than a dedicated vector store means hybrid retrieval is a join instead of a client-side merge across two systems with independent failure modes.

Retrieval

Three strategies behind one interface, selected by config: naive (dense only), hybrid (dense + full-text + symbol, fused by RRF), and hybrid+graph (hybrid, then call-graph expansion). All three stay runnable permanently so the comparison is reproducible at any commit.

Reasoning

A LangGraph state graph. Locate interprets the question and issues retrieval queries. Trace walks the call graph around the located chunks with bounded depth and cycle detection. Synthesize streams a grounded answer with file:line citations. A conditional edge routes back from trace to locate when context is insufficient, bounded by an attempt counter.

Request path

POST /v1/query
  → auth + per-key rate limit (Redis token bucket)
  → cache check (normalized question + repo scope)
  → locate    : hybrid retrieval, repo-scoped
  → trace     : recursive CTE over call_edges, bounded depth
  → synthesize: SSE token stream, citations verified before emit
  → OTel spans exported per stage; result cached

Design decisions

Each one names what was given up. A decision without a stated cost reads as an untested opinion.

Multi-repo, not multi-tenant

Context
The design doc scoped "one codebase at a time" and explicitly cut multi-tenancy. The requirement became "work on any repo".
Decision
Separate the two ideas. Multi-repo indexing is in — a repo registry, repo_id on every chunk, symbol and edge. Multi-tenancy stays cut — no per-org isolation, no auth boundaries between users.
Gave up
Any story about tenant isolation or per-customer data boundaries. That's a different project.
If asked
"Those are different requirements that sound similar. Indexing many repos is a data-modeling problem — scope every row by repo. Multi-tenancy is a security-boundary problem. I built the first and deliberately didn't claim the second."

Tree-sitter tag queries instead of per-language parsers

Context
Supporting "all languages" appears to mean writing an AST walker per language — the thing that makes multi-language support look impossible for one person.
Options
Hand-write extraction per language; or restrict to Python; or find a uniform mechanism.
Decision
Tree-sitter grammars ship queries/tags.scm declaring captures like @definition.function, @definition.class and @reference.call — the same mechanism GitHub uses for cross-language code navigation. One query-driven code path replaces N parsers. Adding a language ships a .scm file, not code.
Verified
Checked across nine grammars before designing around it. Definitions + calls: python, javascript, go, java, rust, ruby, php. Definitions only: typescript, cpp. No queries at all: c_sharp. Built in Phase 2 as 10 individually pinned grammar packages plus two override queries — 11 languages registered, 28 unit tests pinning the exact captures each query produces against real code.
Gave up
Precision. A hand-written walker with type information would resolve calls better. Tag queries are syntactic — they see foo(), not what foo resolves to.
If asked
"Languages carry a declared capability tier rather than silently degrading. Tier 1 gets real call edges; tier 2 gets chunks and approximate edges; tier 3 gets chunks and symbols only. The system reports which tier it used, so nobody mistakes an approximation for analysis."

Rejected a bulk grammar-pack dependency

Context
tree-sitter-language-pack on PyPI offers 371 languages behind one dependency — the obvious shortcut once the tag-query approach was decided, and worth checking before pinning ten packages by hand.
Red flags, checked before adopting
Its API is far larger than "grammar pack" implies — CodeChunk, SymbolInfo, DownloadManager, download_all — and that last pair matters: it fetches compiled native binaries at runtime rather than shipping them in the wheel. Publisher is xberg-io, a commercial org on GitHub created October 2025, not the canonical tree-sitter maintainers. The repo itself is real and active (454 stars, pushed same-day) — this isn't a typosquat — but young and feature-bloated for what should be a thin grammar wrapper.
Decision
Rejected. This project clones and parses arbitrary third-party repositories. A dependency that downloads and dynamically loads native code from the network at runtime reintroduces exactly the supply-chain risk that "tree-sitter parses but never executes" exists to rule out — the exposure moves from the untrusted repo being parsed to the parser itself.
Gave up
Convenience. Ten explicit dependencies and two hand-written override queries instead of one. Each was installed and its tags.scm content inspected directly rather than trusted from memory.
If asked
"I don't reject a dependency for being young — I reject it for what it does at runtime combined with what this system does with untrusted input. A grammar pack that only unpacks wheels at install time would have been a fine shortcut; one that fetches binaries while indexing a stranger's repository is a different risk profile entirely."

Postgres recursive CTE for traversal, networkx as test oracle

Context
The design doc specified networkx for the call graph.
Problem
networkx is in-memory. The edges already live in Postgres, so every query would either load a repo's whole graph or maintain a second persistence format — worse with many repos.
Decision
Traversal behind an interface with two implementations. Production is WITH RECURSIVE … CYCLE (Postgres 14+), which gives bounded depth and built-in cycle detection, repo-scoped, in one query with no memory load. networkx becomes the reference implementation used only in tests.
Bonus
Differential testing: assert both implementations produce identical traversals on fixtures. Two independent implementations agreeing is far stronger evidence than one implementation passing hand-written expectations.
Gave up
Graph algorithms beyond traversal. Centrality or community detection would be painful in SQL — but the system doesn't need them.
If asked
"Why not a graph database? It would mean a second system to run, sync and fail independently, to serve bounded-depth traversal that Postgres does natively. The edges have to live somewhere transactional next to the chunks anyway."

Evals moved ahead of the agent layer

Context
The original plan put the eval harness at days 13–15, after agents and production features.
Decision
Move it to immediately after retrieval lands. "Call-graph expansion improves retrieval" is a retrieval claim — testable with no agents involved.
Reason
If the hypothesis is weak, that is the single most important finding the project can produce. The original schedule discovers it with three days left. It also means every later phase is guarded by a regression harness, which is what "CI for answer quality" actually requires.
Gave up
An impressive demo earlier. The agent pipeline is the flashy part and it now comes later.
If asked
"I sequenced it so the riskiest assumption gets tested first. The agents are engineering I'm confident I can finish; whether the retrieval idea works is the actual unknown."

A real conditional edge in the agent graph

Context
The design doc justified LangGraph with "native support for cycles" — but locate → trace → synthesize is a straight line. The cycles were in the call graph, not the agent graph.
Problem
That's a defensibility hole. The obvious follow-up — "so why not three function calls?" — had no good answer.
Decision
Give the agent graph a genuine cycle: if trace finds insufficient context, route back to locate to re-query with refined terms, bounded by an attempt counter in state.
Gave up
Latency in the retry path, and a new non-termination risk that the attempt counter has to bound.
If asked
"Honestly, for a purely linear pipeline LangGraph would be overkill — three function calls would do. It earns its place because of the retry edge, which needs conditional routing and shared state. I'd rather state that than pretend the linear version justified the dependency."

Reciprocal Rank Fusion for hybrid retrieval

Context
The doc said results are "merged and reranked" without specifying a method.
Problem
Cosine similarity and full-text ts_rank are on incomparable scales. Summing or weighting them requires tuning constants with no principled basis.
Decision
RRF: score each document by Σ 1/(k + rank) across result lists. It consumes ranks, not scores, so scale mismatch stops mattering. Roughly ten lines, no model, no added latency.
Gave up
Some ceiling. A cross-encoder reranker would likely do better — so it becomes a measured upgrade in the eval harness rather than an unexamined default.
If asked
"Dense retrieval is semantically strong and lexically weak. Identifiers need exact matching — ask where dispatch_request is defined and an embedding returns things that feel like request dispatching. That's the argument for hybrid on code specifically."

Local and hosted embeddings behind one interface

Context
Provider undecided; deployment target is a hosted backend.
Tension
Local models mean torch — roughly 2GB in the image plus inference RAM, which a small hosted instance doesn't have. Hosted APIs mean rate limits, which make bulk indexing slow and eval runs non-reproducible.
Decision
Both, behind one interface. Local for dev, CI and evals; hosted for the deployed image. The interface was needed anyway to carry model name and dimension.
If asked
"Embedding provider is chosen by indexing throughput, not answer quality. A free tier with per-minute caps can't embed a few thousand chunks reproducibly, and irreproducible eval runs are worse than slightly worse embeddings."

No ORM

Decision
Raw psycopg and plain numbered SQL migrations.
Reason
The interesting queries — HNSW vector search, RRF fusion, recursive CTE traversal, partition management — are all things an ORM obscures rather than helps. Alembic is heavy when there's no ORM to autogenerate from.
Gave up
Autogenerated migrations and typed row mapping. Both are written by hand instead.

A job boundary the design doc lacked

Context
Indexing an arbitrary repo takes minutes; an HTTP request can't hold it.
Decision
POST /v1/repos returns a job id; a status endpoint reports progress; a worker polls the index_jobs table with heartbeats so a dead worker's job is reclaimed rather than stuck in running forever.
Gave up
Simplicity. Deliberately not Celery — a Postgres job table plus a polling loop is about fifty lines and adds no broker to operate.

Phase log

Numbered because the order is real — each phase depends on the one before it.

Phase 0 — Scaffold and configuration Done

Package layout, typed pydantic-settings config, Docker Compose for Postgres/pgvector, Redis and Jaeger, and a CLI wiring config into the migration runner.

Two details worth being able to defend. Config is a validated object rather than scattered os.environ.get calls because embedding_dim is interpolated into DDL — a string that looks like an int would produce a schema nobody intended — and retrieval_strategy is a closed set, so a typo fails at startup instead of silently falling back to a default and quietly invalidating an eval run. And the runtime container omits the local-embeddings extra entirely, keeping roughly 2GB of torch out of the deployed image while CI and evals still get reproducible local embeddings.

Phase 1 — Schema and migrations Done

Seven tables — repos, files, chunks, symbols, call_edges, index_jobs, api_keys — plus a forward-only migration runner.

What the schema encodes

  • repo_id on every retrievable row, denormalized deliberately. It could be reached by joining through files, but it belongs in the WHERE clause of every query directly, and the recursive CTE would otherwise re-join at every recursion level.
  • chunks partitioned by repo_id — a correctness fix, not an optimization. See the first war story.
  • Composite foreign keys into chunks (repo_id, id), so a cross-repo edge is a constraint violation rather than a silent quality bug.
  • last_indexed_sha from day one, because incremental re-indexing keys off it and backfilling state you no longer have is impossible.
  • files.blob_sha, so an incremental run skips files git reports as touched but whose content is unchanged — reverted edits, formatter rewrites.
  • A generated tsvector column beside the vector, maintained by Postgres so it cannot drift from content.
  • edge_resolution — exact / approximate / unresolved — plus the raw callee name, so approximations stay auditable and are never rendered as certain call paths.
  • One live index job per repo, via a partial unique index on status IN ('queued','running'). Two concurrent indexers would interleave upserts and leave a repo half-indexed behind a last_indexed_sha claiming otherwise.

What the migration runner does beyond running files

  • Drift detection. Each applied migration's sha256 is recorded; editing a file after it applied is a hard error. Prevents the failure where an edit works on a fresh machine and production never applies it.
  • Checksums the raw template, before substitution. Substituted values come from config and legitimately differ between environments; the file must not. Hashing rendered SQL would flag every environment difference as tampering.
  • Advisory lock. Concurrent boots serialize instead of racing on CREATE TABLE — the normal case when several containers start at once.
  • Transactional DDL. Postgres lets DDL participate in transactions, so a migration failing partway leaves no partial schema, and the schema_migrations insert is in the same transaction as the change it records.
  • Dimension verification. After migrating, read the deployed vector dimension via format_type and refuse to boot on a mismatch with config.

Verification: 9 integration tests green against Postgres 17.11 / pgvector 0.8.6 — idempotence, dry run, drift, database-ahead-of-checkout, dimension mismatch, atomicity, and three discovery-validation cases.

Why integration tests, not mocks

Idempotence, drift, atomicity and dimension enforcement are properties of the runner's interaction with database state. Mocking psycopg would assert that the mock behaves like the code — always true, proves nothing. The same reasoning produced the measured HNSW finding below.

Phase 2 — Language layer Done

A grammar registry and one query-execution path (extract_tags) that every tier1/tier2 language runs through. Nothing in that function is language-specific — language knowledge lives entirely in query text, verified against real parse trees before being written.

What got built, and what got rejected first

The obvious shortcut for "all languages" was a bulk grammar-pack dependency — 371 languages behind one pip install. Checked before adopting it and rejected: its API downloads compiled native binaries at runtime, published by a young commercial org, not the canonical tree-sitter maintainers. For a system that parses arbitrary third-party repositories, that is the wrong place to introduce a runtime network fetch of native code. See the decision above for the full comparison. Ten official grammar packages are pinned individually instead, each verified by installing it and inspecting its actual tags.scm content directly — not assumed from documentation.

Two gaps needed override queries, and both surprised in a different way

  • TypeScript's own tags.scm is missing more than call references — no function_declaration or class_declaration at all, only the abstract_* variants. Ordinary code produces nothing from the upstream query alone. The fix borrows JavaScript's patterns directly, verified by parsing real TypeScript — including confirming the same query survives JSX syntax in the separate TSX grammar, since .tsx uses a different grammar entry point than .ts.
  • C++ has definitions but zero call references, and both obj.method() and obj->method() turned out to resolve to the identical field_expression node shape in this grammar — one override pattern covers both syntaxes, confirmed by parsing both forms rather than assumed from C++ syntax rules.

A mechanical trap that would have silently produced wrong data

tree-sitter's Python API offers two ways to run a query: QueryCursor.captures() returns a flat dict per capture name, and QueryCursor.matches() groups captures by which pattern match they came from. Multi-function files exposed the difference — .captures() would in general lose the correspondence between a specific @name and its @definition.function when several functions exist in one file, since both land in the same flat list with no guaranteed alignment between them. extract_tags uses .matches(), and test_multiple_definitions_paired_with_correct_names pins the correct pairing so a future refactor toward the more obviously named .captures() method fails loudly instead of silently mislabeling functions.

Verification: 28 unit tests green — 11 languages detected correctly by extension, tier assignment for all three tiers, real extraction against Python/JavaScript/TypeScript/TSX/C++/C#, JSX parsed without error in both the plain JS and TSX grammars, the #not-eq? predicate confirmed to actually exclude constructor from method definitions (proving real tree-sitter predicates are honored, not just silently ignored), and confirmation that non-definition captures like @doc and @local.scope never leak into results.

War stories

Each in a fixed shape — symptom, investigation, root cause, fix, lesson — because that's the shape the question arrives in.

Measured, not reasoned

A vector search that returned nothing while the data was right there

Symptom
A repo-scoped nearest-neighbour query returned zero rows despite 500 valid matches in the table. No error, no warning — a successful query returning an empty set.
Setup
30,500 vectors across three repos; the target repo held only 500 of them, and they were the farthest from the query. Asked for the 10 nearest chunks in that repo.
Root cause
HNSW is an approximate index. Postgres searches the index first and applies WHERE repo_id = N afterwards. The nearest neighbours all belonged to other repos, so they were found, then filtered away, leaving nothing. Classic ANN filtered-search failure.
Measured
ConfigurationRows returned
Unpartitioned, ef_search=40 (default)0
Unpartitioned, iterative_scan=relaxed_order0
Unpartitioned, + scan_mem_multiplier=410
Unpartitioned, ef_search=100010
Partitioned by repo_id, defaults10
Fix
Partition chunks BY LIST (repo_id). Partition pruning means the scanned partition contains only matching rows — there is no post-filtering step, so there is no recall to lose. Correct at default settings.
Lesson
Every other row in that table is tuning — spend more search effort until the filter probably finds enough. Partitioning removes the failure mode instead of making it less likely. Prefer fixes that change what's possible over fixes that change what's probable.
The obvious fix didn't work

pgvector's purpose-built feature for this didn't fix it

Expectation
hnsw.iterative_scan, added in pgvector 0.8, exists precisely for filtered search — it keeps fetching candidates until enough rows survive the filter.
Symptom
Still zero rows. Raising hnsw.max_scan_tuples from 20,000 to 40,000 — past the full 30,500-row table — changed nothing.
Investigation
Swept both budget knobs independently. max_scan_tuples alone never helped; adding scan_mem_multiplier=4 immediately returned all 10.
Root cause
relaxed_order buffers candidate tuples in memory bounded by work_mem × scan_mem_multiplier. The buffer filled long before the scan reached the target repo's rows. Memory was the binding constraint, not the tuple budget — so the knob that looked relevant was the wrong one.
Lesson
Two knobs that both look like "scan further" can bind differently, and the documentation-obvious one wasn't it. This is the concrete reason the project verifies behaviour against a real database instead of reasoning from API names.
The database suggested the wrong fix

A hint that would have silently disarmed a database-wide guarantee

Symptom
After adding composite foreign keys, dropping a repo's partition failed: cannot drop table chunks_repo_2 because other objects depend on it. Postgres helpfully suggested DROP … CASCADE.
Why the hint is a trap
Those FK constraints are defined on the parent tables — symbols and call_edges — and shared by every repo. CASCADE drops the constraints themselves. Deleting one repo would have quietly removed the cross-repo guarantee for the entire database, and nothing would have failed at the time.
Fix
Delete the dependent rows for that repo, then DETACH PARTITION, then DROP TABLE. Verified that Postgres validates the FKs on detach and refuses to strand rows — tested by trying it with dependents still present and confirming it errors.
Lesson
An error hint optimizes for making the current statement succeed, not for preserving your invariants. Two fixes that were individually correct — partitioning and composite FKs — interacted in a way neither anticipated, and only running the teardown path revealed it.
Subtle by design

Checksum the template or the rendered SQL?

Context
Migrations contain ${EMBEDDING_DIM}, substituted from config, because pgvector needs a fixed dimension at DDL time while the embedding model is configurable.
The question
Drift detection hashes migration files. Hash the raw template, or the SQL actually executed?
Decision
The raw template. Substituted values legitimately differ between environments — dev on 384, prod on 768. Hashing rendered SQL would flag every environment difference as tampering, and an alarm that fires on normal operation is an alarm you learn to ignore.
Consequence
The dimension is then unguarded by the checksum, so it needs its own check: read the deployed column type via format_type and refuse to boot on mismatch. Vectors from different models still produce well-formed similarity scores — they're just meaningless, and every downstream eval number inherits the corruption.
Lesson
"The file is immutable, the config may vary" is the actual invariant. Getting the checksum boundary wrong would have produced either false alarms or a silent gap.

Question bank

Answers are collapsed on purpose.

Try answering out loud before opening each one. Recognizing an answer feels like knowing it and isn't.

On retrieval

Why Postgres with pgvector instead of a dedicated vector database?

Hybrid retrieval needs dense vectors, full-text ranking and an exact symbol index combined. In one database that's a join. Across two systems it's a client-side merge with two sets of credentials, two failure modes and a consistency problem when indexing writes to one and not the other.

The call graph also has to live somewhere transactional next to the chunks, and the traversal is a recursive CTE over those edges. Splitting vectors out would leave the majority of the interesting queries in Postgres anyway. At this scale a dedicated vector DB buys throughput I don't need at the cost of an integration I'd have to maintain.

What does HNSW actually give up compared to exact search?

Recall. Exact search compares the query against every vector — perfect results, cost linear in table size. HNSW builds a multi-layer navigable graph and walks it greedily, which is dramatically faster and will sometimes miss a true top-k neighbour. m controls graph connectivity; ef_construction controls build-time search width; ef_search controls query-time width. Higher means better recall, slower builds, more memory.

The failure that actually bit me wasn't ordinary recall loss — it was the interaction with filtering, where approximate search plus a post-applied WHERE can return nothing at all.

Why is hybrid retrieval worth the complexity over dense-only?

Because code is full of identifiers, and identifiers are lexical rather than semantic. Ask "where is dispatch_request defined" and a pure embedding search returns functions that feel like request dispatching — semantically close, exactly wrong. Full-text search and an exact symbol index catch what embeddings blur, and RRF fuses the ranked lists without needing their scores to be comparable.

How does RRF work, and why not just weight the scores?

RRF scores each document as Σ 1/(k + rank) summed across result lists, where k is a damping constant (60 is conventional). It consumes ranks, not scores.

That's the point. Cosine similarity lives roughly in [-1, 1]; Postgres ts_rank has no fixed range. Weighting them requires constants with no principled basis that you'd retune whenever either component changed. Ranks are comparable by construction.

On the call graph

What happens if a query hits a function that calls into a cycle?

Traversal is bounded on two axes: a maximum depth, and cycle detection. Postgres has a CYCLE clause on recursive CTEs that maintains the visited path and marks a row when it revisits a node, so traversal terminates on cyclic graphs natively rather than by hand-rolled bookkeeping.

It's tested against a deliberately cyclic fixture, and against a networkx BFS implementation that must produce identical output — differential testing rather than trusting one implementation.

How accurate is your call graph, really?

It's syntactic, and I'd rather say that plainly than oversell it. Tag queries see a call site named foo; resolving which foo is genuinely hard in a dynamic language. There's no type inference and no dynamic-dispatch resolution, so self.handler() often can't be pinned to one target.

So every edge carries a resolution class — exact, approximate, or unresolved — and the raw callee name is kept alongside it. Approximate edges are never presented as certain call paths. The honest claim is "high-value approximation with stated limits", not "static analysis".

Why not a graph database for the call graph?

The workload is bounded-depth traversal from a small seed set — three or four hops, not arbitrary pattern matching. Postgres does that in a recursive CTE with built-in cycle detection. A graph database would be a second system to run, sync and fail independently, and the edges still need to sit transactionally beside the chunks they reference.

If the workload became global graph analytics — centrality, community detection — that calculus changes. It hasn't.

On the agents

Why LangGraph? Isn't this just three function calls?

For a purely linear locate → trace → synthesize pipeline, that criticism is fair and I'd concede it. What earns the dependency is the conditional edge: when trace finds insufficient context, the graph routes back to locate to re-query with refined terms, bounded by an attempt counter in shared state.

That needs conditional routing over accumulated state, which is exactly what a state graph provides. Worth noting the original design justified LangGraph with "support for cycles" while the cycles were in the call graph, not the agent graph — I caught that conflation and added a real cycle rather than leave the justification hollow.

What stops the model from inventing a citation?

Grounding is a deterministic function, not a prompt instruction. Every claimed citation is checked: does that chunk exist in the context we actually assembled, and does the claimed line range actually exist in that file? Citations that fail are dropped before rendering, and the check is unit-tested on both accept and reject paths, including a fabricated line range.

The limit worth stating precisely: this verifies the citation, not the claim. It proves the cited code exists and was retrieved. It cannot prove the sentence attached to it is a correct description. Faithfulness is measured separately in the eval harness.

On engineering judgment

How do you decide whether to trust a dependency?

By what it does at runtime combined with what the system does with untrusted input — not by how convenient it is. A bulk grammar-pack library offering 371 languages in one dependency looked like an easy win right up until I read its API and found DownloadManager and download_all: it fetches compiled native binaries over the network at runtime, from a commercial org created a few months earlier, not the canonical tree-sitter maintainers.

That's disqualifying specifically here, because this system clones and parses arbitrary third-party repositories. A dependency that downloads and dynamically loads native code while indexing a stranger's repo reintroduces exactly the supply-chain risk that "tree-sitter parses but never executes" is supposed to rule out. I checked PyPI metadata, the GitHub org's creation date, and the package's actual exported API before deciding — not just the star count. Ten official packages, individually pinned, cost more typing and bought a supply chain I could actually reason about.

How do you know call-graph expansion actually helps?

Because it's measured rather than asserted. There's a labeled set of Flask questions with known-correct files and symbols, and a runner reporting precision@k and recall@k for three strategies: naive dense retrieval, hybrid, and hybrid plus graph expansion.

The naive baseline was built first specifically so there'd be something to measure against, and it's never deleted — it stays config-selectable permanently, so the comparison is reproducible at any commit. The usual way this fails is refactoring the baseline out of existence and losing the ability to reproduce the claim.

Why partition rather than tune ef_search?

Tuning makes the failure less likely; partitioning makes it impossible. With ef_search=1000 the query worked in my test, but that's a number chosen against one data distribution — a repo with a different shape, or more repos, moves the threshold and the failure returns silently.

With one partition per repo, WHERE repo_id = N prunes to a single partition where every row already satisfies the filter. There's no post-filtering step, so there's no recall to lose, at default settings, regardless of distribution.

What did partitioning cost you?

Three things. A partition must be created when a repo is registered, so registration does DDL. The primary key must include the partition key, making it (repo_id, id), so everything referencing chunks uses composite foreign keys. And foreign keys referencing a partitioned table create one catalog constraint entry per partition, so constraint count grows with repo count — fine at tens to hundreds, worth revisiting beyond that.

The composite-FK consequence turned out to be a benefit: a cross-repo edge is now a foreign-key violation. The scoping invariant stopped being something to remember and became something the database enforces.

Your system supports "all languages" — how, realistically?

Through one query-driven code path, not N parsers. Tree-sitter grammars ship queries/tags.scm declaring @definition.function, @definition.class and @reference.call. The extractor runs those queries, so adding a language ships a .scm file rather than code.

Support isn't uniform, and the system declares that rather than hiding it. Tier 1 grammars have both definitions and call references — verified for Python, JavaScript, Go, Java, Rust, Ruby and PHP. TypeScript and C++ ship definitions only, so calls are approximated by symbol name. C# ships no tag queries, so it gets chunks and symbols until someone writes them.

Is it safe to index a repository you don't control?

The core property is that tree-sitter parses but never executes. Indexing untrusted code never runs it — no imports, no build step, no evaluation. That's safe by construction rather than by sandboxing.

The real exposure is the clone, not the parse: a server fetching a user-supplied URL needs an SSRF guard, --depth 1, a size cap, a clone timeout and a disk quota. Those are the controls on the ingestion path.

What's the weakest part of the system?

Call resolution. Everything downstream — trace quality, multi-hop answers, the entire differentiating claim — depends on caller/callee edges being right, and they're derived from syntax without type information. In a dynamic language a meaningful fraction of call sites can't be resolved to a single target.

That's why edges carry a resolution class, why approximations are never presented as certainties, and why per-stage failure attribution is in the eval harness — so a bad answer can be traced to the stage that caused it rather than blamed on "the LLM".

How would you scale this to ten thousand repositories?

The current design would strain in two known places. Partition-per-repo means catalog growth and planning-time cost at that count, so I'd move to hash partitioning with a bounded partition count, accepting some in-partition filtering back — and re-measure the filtered-recall behaviour, since that's exactly the tradeoff being reversed.

The second is indexing throughput: one polling worker doesn't scale, so jobs would need claiming via SELECT … FOR UPDATE SKIP LOCKED across multiple workers. The partial unique index on live jobs already keeps one repo from being indexed twice concurrently, so that part holds.

What would you do differently if you started over?

I'd verify database behaviour before writing schema, not after. The partitioning decision came from measuring a filtered vector search, and that measurement could have happened on day one — instead it revised a schema I'd already written and documented.

More generally: the sequencing lesson from moving evals earlier applies to infrastructure too. Test the assumption you'd most regret being wrong about, first.

Known limits

Volunteering these is stronger than being caught by them.

  • Call resolution is syntactic. No type inference, no dynamic dispatch. Some call sites resolve to nothing or to the wrong target; edges are labelled with confidence accordingly.
  • Not multi-tenant. Many repos, no isolation boundary between users. Stated as a scope cut, not an oversight.
  • Partition-per-repo has a ceiling. Catalog constraint entries grow with repo count. Comfortable at tens to hundreds.
  • Grounding verifies citations, not claims. It proves cited code exists and was retrieved, not that the sentence describing it is correct.
  • English text-search config on source code. Stemming identifiers with English rules is a compromise; whether simple does better is a measurable question the eval harness can settle.
  • Tier 2 and 3 languages get degraded call graphs — approximate or absent. Declared per language rather than silently applied.
  • No numbers claimed until measured. No precision@k or latency figure goes in the README or on a résumé before the harness produces it. A modest measured number is defensible; an impressive invented one collapses on the second question.

Glossary

Terms this project uses that an interviewer may ask you to define cold.

CST
Concrete syntax tree — tree-sitter's output. Unlike an AST it preserves every token including punctuation and comments, which is what makes exact line spans recoverable.
Tag query
An S-expression pattern in tags.scm that captures definitions and references from a parse tree. The uniform mechanism behind multi-language support.
HNSW
Hierarchical Navigable Small World — an approximate nearest-neighbour index built as a layered proximity graph, traversed greedily.
RRF
Reciprocal Rank Fusion — combines ranked lists by Σ 1/(k + rank), using positions rather than scores so incomparable scales don't matter.
Recursive CTE
A self-referencing SQL common table expression. Postgres 14+ adds a CYCLE clause that tracks visited paths, giving cycle-safe graph traversal in one query.
tsvector
Postgres's parsed, normalized full-text representation. Here a generated column, so it can't drift from the content it indexes.
Partition pruning
The planner excluding partitions that can't match a predicate. The mechanism that makes repo-scoped vector search exact rather than approximate-then-filtered.
Token bucket
Rate-limiting scheme where a bucket refills at a steady rate and each request spends a token. Permits bursts up to bucket size, unlike a fixed window.
SSE
Server-Sent Events — one-directional server→client streaming over plain HTTP. Sufficient for token streaming and simpler than WebSockets.
Precision@k
Fraction of the top k results that are relevant. Recall@k is the fraction of all relevant items appearing in the top k.
